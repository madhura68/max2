### Gebruiker

### Model

Vier vragen om de prompt scherp te krijgen:

1. Waar draait de prompt: Claude Code met toegang tot het bestandssysteem van max2, of plak je de logs er zelf in? [standaard: Claude Code op max2 dat de run-log-map zelf leest]
2. Wat is "vannacht" precies aan tijdsgebied? [standaard: 22:00 gisteren tot 07:00 vanochtend, UTC]
3. Wat moet het resultaat zijn: alleen een rapport (per mislukte job: run-id, foutcode, oorzaak), of ook voorgestelde reparaties? [standaard: alleen rapport met oorzaak per job; geen reparaties]
4. Mag Opus ook de triage-oordeelen uit `/worker-insights` meenemen, of alleen de run-logs op schijf? [standaard: alleen de run-logs op schijf; triage-oordeel erbij als het er toevallig is]

### Gebruiker

Akkoord met je voorstellen. Het gaat om de harness-worker op max2.

### Model

De documentatie bevestigt het run-log-contract (spec `specs/2026-09-28-harness-run-logging-design`, §5): mislukte runs staan herkenbaar in `/srv/scrum4me/worker-logs/harness/max2/runs/<YYYYMMDDTHHMMSSZ>.log` via een `ERROR <CODE>: <bericht>`-regel, `harness done … exit_code=1` en een `harness.run_end` met outcome `failed` of `abandoned`. De prompt is klaar:

```
<context>
Ik draai een agent-harness-worker (pool `harness`, instance `max2`) op max2. Vannacht zijn mogelijk jobs mislukt en ik wil die in één oogopslag terugzien. De run-logs liggen op schijf op max2; dit prompt draai ik in Claude Code op max2 zelf, dus je hebt directe toegang tot het bestandssysteem.
</context>

<task>
Zoek in de run-logs van de harness-worker alle mislukte jobs uit het venster van vannacht en lever erover een rapport.
</task>

<constraints>
- Logmap: `/srv/scrum4me/worker-logs/harness/max2/runs/`. Bestandsnamen zijn `<YYYYMMDDTHHMMSSZ>.log` en de tijdstempel is het UTC-moment direct na de claim (run-log-contract, spec `specs/2026-09-28-harness-run-logging-design` §5.1).
- "Vannacht" = van 22:00 UTC gisteren tot 07:00 UTC vanochtend. Selecteer op basis van de tijdstempel in de bestandsnaam.
- Een run is mislukt als één van deze geldt: een meta-regel `ERROR <CODE>: <bericht>`, een regel `harness done job_id=… exit_code=1`, of een JSON-regel `harness.run_end` met `outcome` `failed` of `abandoned`. Een log zonder `exit code=`-regel (mogelijk harde crash, run blijft "running") noem je afzonderlijk als "onafgesloten" en niet als mislukt.
- Per mislukte run: run-id/tijd, job_id, de foutcode, het foutbericht, de jobsoort (IDEA_CHAT of TASK_IMPLEMENTATION, uit de `config`-regel) en het model. Waar het uit het log haalbaar is: op welk punt de run faalde (bijvoorbeeld `harness.loop_end` met status, containerstap of jobstap).
- Als er voor een run een triage-oordeel beschikbaar is in `/worker-insights` (scrum4me-workers of ops_dashboard-database op max2), voeg het toe; is het niet te vinden, vermeld dan "geen triage-oordeel beschikbaar" en ga door.
- Rapport alleen: pas niets aan, herstart niets, herlaai geen jobs.
</constraints>

<done_when>
Elk `.log`-bestand in de map valt binnen of buiten het venster, en elk bestand binnen het venster staat in het rapport: als mislukt (met foutcode en oorzaak), als geslaagd (samengevat), of als onafgesloten.
</done_when>

<output_format>
Een rapport in het Nederlands: eerst een kort overzicht (aantal runs in het venster, aantal mislukte, foutcodes in frequentie), daarna per mislukte run een blok met de gevraagde velden, ten slotte de geslaagde runs in één regel per run.
</output_format>
```

Aannames:
- "Vannacht" is 22:00 UTC gisteren t/m 07:00 UTC vanochtend (conferentietijd UTC, conform de tijdstempels in de bestandsnamen).
- De rapporttaal is Nederlands en het resultaat lees ik zelf als input voor reparatie.
- Triage-oordeelen uit `/worker-insights` mogen erbij als ze te vinden zijn; als de database of de app niet bereikbaar is, stopt Opus niet.
- Er staan alleen harness-logs in de map (pool `harness`); andere pools liggen in andere mappen en vallen buiten het venster.
- Opus hoeft de OOM-/crashdetectie niet te doen: een ontbrekend afsluitblok noemt het "onafgesloten".
