### [MAJOR] A recorded pathname is not continuing proof that the file belongs to the app
**Where:** `doc:201`, `doc:216`, `doc:238–250`, `doc:268–273`.

**Claim:** NF4 forbids deleting foreign files; recovery deletes existing paths recorded as `temp_path` in pending actions.

**Reality:** Ownership records contain a pathname, not evidence that the object currently at that pathname is the exclusively created object. For example: route C creates and records a final file, crashes halfway through copying, and another process removes that incomplete file and places an unrelated file at the same name before MacSearch restarts. Line 250 directs recovery to delete the replacement merely because the recorded path exists. A related route B window exists after publication: the old temporary pathname remains recorded until the final update, although the owned object has moved elsewhere. A foreign file subsequently created at that old path can be deleted after a crash. AC3a checks a foreign file at a different pathname, so that test can pass with this defect present.

**Consequence:** Recovery can delete a file that is not the app's, directly violating NF4. This is separate from, and not covered by, the accepted incomplete-final-file trade-off.

**Fix:** Specify a recovery ownership mechanism that does not equate pathname existence with ownership, and fail closed when safe deletion cannot be established. Account for replacement between checking ownership and deleting; a separate identity check followed by an unconditional pathname unlink is not by itself sufficient. Retire route B's cleanup reference after publication. Add recovery tests replacing the exact recorded pathname with foreign content, including the route B post-publication window, and require the replacement to survive.

### [MAJOR] Route C retries require a database record that has not yet been inserted
**Where:** `doc:143`, `doc:217–218`, `doc:235–246`, `doc:265–267`.

**Claim:** Every retry updates the existing action record, never inserts a second record, and resumes route C at its exclusive-create step.

**Reality:** Route C inserts its first pending record only after successful exclusive creation in step 3. If another process creates the chosen destination between F16 and step 2, `open` returns `EEXIST` before any action record exists. For different content, the shared retry rule then requires updating `dest_path` in an existing record. No such record exists. F19b explicitly handles the no-record case for an identical skip, but not this different-content retry or exhaustion before any successful creation. The route C collision test only asserts preservation of the foreign file and absence of an unsafe rename; it does not assert a successful suffixed result or exactly one terminal action record.

**Consequence:** A normal collision path has no implementable bookkeeping sequence as written. Implementers must invent behavior, potentially failing a valid transfer or losing its action log, despite the claimed retry fix.

**Fix:** Distinguish retries before first exclusive creation from retries after record insertion. Before a record exists, recompute the candidate and retry creation without an update; after successful creation, insert exactly once. Specify a terminal action insert for exhaustion before creation. Retain the existing-record rule once a record exists. Strengthen route C collision and exhaustion tests to assert destination content, source preservation/removal as appropriate, exactly one terminal record, and no pending record left.
