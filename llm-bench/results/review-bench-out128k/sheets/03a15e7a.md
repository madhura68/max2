## Findings

### [MINOR] Route C: crash between completed copy and `temp_path = NULL` deletes a complete file
**Where:** NF4 Route C, step 4 → step 5 (lines 239–240 `sources/doc`)

**Claim:** `temp_path = NULL` marks the file as complete; after that the file will not be cleaned up on crash. Before that, crash cleanup deletes only half-written files.

**Reality:** If the app crashes after step 4 (copy + dates completed) but before step 5 (the `temp_path = NULL` update), the file on disk is **complete**, yet crash cleanup (NF4 line 250) deletes it because `temp_path` still points to it. This is outside the accepted trade-off, which explicitly covers *half-written* files only.

**Consequence:** A complete file is needlessly deleted on restart. The source is always intact (for move, source deletion happens in a later step), so there is no data loss, but the user must re-run the transfer. Unnecessary rework.

**Fix:** Combine steps 5 and 6 into a single database operation (`UPDATE file_action SET temp_path = NULL, result = ? WHERE …`). This eliminates the window where a complete file still has `temp_path` set. Alternatively, document the accepted rework risk explicitly.

---

### [MINOR] Route C: retry after first `EEXIST` at step 2 references a non-existent record
**Where:** NF4, retry section, line 246 (`sources/doc`)

**Claim:** \"`dest_path` in het bestaande record wordt bijgewerkt\" — meaning on the retry path the code updates an existing record.

**Reality:** For Route C the first `EEXIST` occurs at step 2 (`O_EXCL` creation), which is **before** step 3 (insert pending record). No record exists to update. The retry section then says \"ga verder bij route C stap 2\" without handling the missing-record case. An implementation that literally follows this text would attempt a database update on a non-existent row, causing an error.

**Consequence:** Spec ambiguity that could cause a runtime crash in the implementation.

**Fix:** Clarify that for Route C on the first `EEXIST` (before a record is created), the `dest_path` update is skipped. Text: \"Bestaat er nog geen record (route C, eerste poging), dan wordt deze stap overgeslagen en gaat de app direct verder bij route C stap 2.\"

---

### [MINOR] Route A: non-`EEXIST` errors from `renamex_np` are not explicitly handled
**Where:** NF4 Route A, steps 1–4 (lines 220–224 `sources/doc`)

**Claim:** The only error mentioned for `renamex_np` is `EEXIST` (triggers a retry). All other errors are implicitly covered by the general framework.

**Reality:** `renamex_np` can fail with `EACCES` (permissions), `ENOENT` (source deleted between step 2 and step 3), `EROFS` (read-only volume), or other OS errors. Route A has no explicit handling for these. The pending record would remain in `pending` state with no cleanup path, violating the invariant that every record ends in a final result. While F17 says \"een fout bij één bestand stopt de batch niet\", the connection between a route-level OS error and the record lifecycle is not spelled out.

**Consequence:** A non-`EEXIST` failure could leave an orphaned `pending` record in the database, making the run appear incomplete.

**Fix:** Add a sentence: \"Bij een andere fout dan `EEXIST` wordt het record bijgewerkt naar `failed`, blijft het bronbestand staan (voor verplaatsen) en gaat de batch door.\"
