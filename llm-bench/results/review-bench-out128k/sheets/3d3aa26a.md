## Findings

### [MAJOR] Recorded path is not sufficient proof of ownership at deletion time
**Where:** `doc`, lines 196–203, 213–216, 229, 238, 248–251; acceptance cases at lines 268 and 273.

**Claim:** A file is app-owned when it was exclusively created and its path was recorded before writing. Startup deletes any existing file at a pending action's `temp_path`; other files are never deleted.

**Reality:** Exclusive creation proves ownership of the object originally created, not of future occupants of its pathname. A concrete route C sequence is: create the final file exclusively, insert its pending record, write part of it, crash; another process removes/replaces that file with a foreign file at the same final name; restart. The prescribed cleanup sees that `temp_path` exists and deletes the foreign replacement. No concurrent operation during cleanup is necessary for this counterexample. Route B has the same problem at its recorded temporary path. Its old temporary pathname also remains recorded after successful publication, so a replacement appearing there can be deleted after a crash even though the published file is complete and its source may already be gone. The schema contains no persisted object identity, and cleanup specifies no identity check. The tests protect foreign files at different paths, which does not exercise this failure.

**Consequence:** The implementation can violate the binding prohibition against deleting a foreign file. This is distinct from, and does not challenge, JP's acceptance of an app-owned half-written route C file.

**Fix:** Repair ownership tracking and cleanup: persist sufficient identity information for the exclusively created object, verify that the current object is still that object before deletion, and preserve files when ownership cannot be established. Specify how deletion avoids a replacement race rather than relying solely on a pathname check. Add a crash/restart test that replaces the recorded `temp_path` with foreign content and asserts that the replacement survives. Apply the same ownership requirement to error cleanup.

### [MAJOR] Route C retries assume a record that has not yet been inserted
**Where:** `doc`, lines 143–144, 217–218, 235–246; AC3a at line 267.

**Claim:** Every retry updates the existing record, never inserts a second record, and resumes route C at step 2 after updating `dest_path`.

**Reality:** In route C, `open(O_EXCL)` is step 2 and the first pending insert is step 3. If the first open returns `EEXIST`, there is explicitly no app-owned file and there is also no pending record. If renewed F16 finds a different-content collision followed by a free candidate, line 246 nevertheless requires updating `dest_path` in an existing record before resuming step 2. That record does not exist. F19b explicitly handles the no-record identical outcome, but there is no corresponding rule for the different-content retry. Route C's eventual step 3 also says to insert, whereas the general retry rule says always update. The route C collision test only requires preservation of the foreign file and absence of an unsafe rename; an implementation that fails the transfer instead of retrying can satisfy those assertions.

**Consequence:** The specified algorithm is inconsistent at the first route C collision. A literal implementation can fail or abort instead of selecting the next candidate, and implementers must invent an exception to the normative bookkeeping rule.

**Fix:** Make record existence explicit: before route C has successfully created its file, retry name selection/open without a record update; after successful exclusive creation, insert exactly one pending record. An identical outcome before creation inserts a terminal record as F19b already specifies. Restrict the existing-record update rule to cases where a record exists. Extend route C collision acceptance to require the expected successful result, unchanged foreign content, exactly one terminal record, no pending record, and correct source retention/removal for the chosen mode.

### [MINOR] Same-volume move conflicts disagree about the logged result
**Where:** `doc`, lines 131–132, 220–224, 266.

**Claim:** A different-content conflict produces `renamed` under F16, while route A always updates to `moved`, including its collision acceptance case.

**Reality:** The same suffixed same-volume move is assigned two different terminal result values. Since the summary groups by result, this is observable rather than merely naming style.

**Consequence:** Implementers and tests can disagree about whether the run's conflict appears in the `renamed` or `moved` count.

**Fix:** State one precedence rule. The smallest change consistent with F16 is to log `renamed` when a suffix was used, including route A, while still asserting that the source is gone.
