## Findings

### [BLOCKER] A recorded pathname is not continuing proof of ownership

**Where:** `doc:196–204,213–216,248–250`; tests at `doc:268,273`.

**Claim:** NF4 forbids deleting a foreign file. Startup cleanup deletes only app-owned files identified by `temp_path` in pending records.

**Reality:** The schema records a path, not the identity of the exclusively created file, and line 250 authorizes deletion merely because that path still exists. A concrete route C sequence is: create final file P exclusively; insert its pending record; write half the data; crash; another application or the user removes P and creates a different file at P; restart. The specified cleanup deletes the foreign replacement. Route B has the same problem with a replaced temporary file, including reuse of its former temporary pathname after successful publication but before the final database update. Exclusive creation proves ownership at creation time, not ownership of whatever later occupies the pathname. The tests protect a foreign file at a *different* pathname, so they pass despite this defect.

**Consequence:** Startup can destroy unrelated data, violating the binding prohibition on deleting foreign files. This is separate from, and not justified by, the accepted half-written-file trade-off.

**Fix:** Repair the ownership protocol: persist an identity for the created object and make cleanup fail closed when that object cannot be verified. Explicitly address replacement between verification and deletion rather than claiming that a pathname or a non-atomic check suffices. If safe deletion cannot be established in a shared destination, leave the ambiguous file in place and report it. Add tests replacing the recorded route B and route C objects with foreign files before restart, plus coverage for the replacement race during cleanup.

### [MAJOR] Route C's first collision enters an existing-record retry without a record

**Where:** `doc:143,217–218,235–246`; tests at `doc:265,267`.

**Claim:** Every retry updates the existing record, never inserts a second record, and the identical-content branch updates that record to `skipped_identical`.

**Reality:** Route C attempts exclusive creation in step 2 and inserts the pending action only in step 3. An `EEXIST` at step 2 therefore occurs before any action exists. Nevertheless, the different-content retry requires updating `dest_path` in the existing record, and the identical-content retry also requires updating an existing record. F19b supplies a no-record insertion rule for `skipped_identical`, but NF4's retry text does not acknowledge it and still leaves the different-content and three-collision exhaustion branches without coherent bookkeeping. Route C's own step 2 explicitly confirms that there is not yet an owned file.

**Consequence:** Implementers must invent an exception to the normative retry algorithm. Literal application either fails the database update or omits the action, undermining the one-record act log and potentially aborting otherwise valid transfers.

**Fix:** Repair the retry rules to distinguish whether an action already exists. For route C collisions before successful creation, choose another candidate without updating a nonexistent action; after successful exclusive creation, insert exactly one pending action before writing bytes. Define direct terminal insertion for identical content and exhausted attempts when no action exists. Extend route C tests to cover different-content retry, identical-content retry, and three `EEXIST`s, each asserting exactly one terminal action and no pending action.

### [MINOR] Route A's collision result contradicts the conflict-result rule

**Where:** `doc:131–132,220–224,266`.

**Claim:** Different-content conflicts use a suffixed destination and produce `renamed`; route A ends with `moved`, and its collision test explicitly expects `moved` under the next free name.

**Reality:** The same successful suffixed move is assigned two different result categories. Route B refers to the general end result, while route A fixes it to `moved`.

**Consequence:** The summary and per-file log can classify conflicts differently depending on publication route, and tests cannot consistently enforce F16.

**Fix:** Repair with one explicit result-precedence rule. If suffix use means `renamed`, update route A and its collision assertion accordingly; otherwise revise F16 to describe the intended move-specific classification.
