## Mechanism check requested by JP's 2026-10-16 decision (never overwrite or delete a foreign file)

- **Writes:** every byte goes to the fd obtained from `open(O_CREAT|O_EXCL|O_WRONLY)`; the fd, not the path, is the write target, so a same-name file that appears after the create can never be overwritten. Route C step 2 explicitly notes there is no own file on EEXIST (doc:237). Temp-name collision never touches the existing file (doc:228).
- **Deletes during a run:** only `temp_path` (doc:249), and the app-file definition (doc:216) requires exclusive creation in this run plus a recorded `temp_path` before any bytes are written — the order in routes B and C (record insert before copy) satisfies this. Source deletion in move mode happens only after publish (route B step 6, doc:232) or after `temp_path = NULL` (route C step 5, doc:240); source-deletion failure never cascades to a delete (F17, doc:132).
- **Crash cleanup:** scoped to runs being set to `interrupted` at start (F19c, doc:152), only paths recorded as `temp_path` in `pending` records, only if they still exist, and explicitly "other files are never removed by cleanup" (doc:250). A published file's record no longer names a live temp (route B: the temp was renamed away; route C: `temp_path = NULL`), so a complete destination is never in the cleanup set — including the crash-after-`temp_path=NULL`-before-source-delete window, which is accepted and tested (doc:269). The sole theoretical hole is that deletion is path-based rather than identity-based; see M3.
- **macOS implementability:** `getattrlist`/`VOL_CAP_INT_RENAME_EXCL` (macOS 10.13+), `renamex_np` with `RENAME_EXCL` (APFS), `O_CREAT|O_EXCL` on exFAT/SMB, and `fcopyfile` with `COPYFILE_ALL` are all real, documented, and appropriate for this use. Nothing unimplementable found.

## Findings

### [MINOR] AC3a lacks the Route B crash case for the publish→record-update window
**Where:** `doc` AC3a (doc:257-273) vs NF4 route B steps 5–7 (doc:231-233) and crash cleanup (doc:250).
**Claim:** AC3a covers Route C's analogous window ("crash na `temp_path = NULL` maar vóór het verwijderen van de bron", doc:269) and generic crash cleanup (doc:273).
**Reality:** No case covers a crash in Route B after the `renamex_np` in step 5 succeeds but before the step-7 record update — in particular for move mode, where step 6 has already deleted the source. The record is still `pending` with `temp_path` pointing at the (now nonexistent) temp, the destination is complete, and the source is gone. The design is safe here: cleanup is gated on `temp_path` and "alleen als ze nog bestaan" (doc:250), so it is a no-op. But the safety rests precisely on cleanup using `temp_path`, not `dest_path` — a regression to `dest_path` would delete a complete file whose source is already gone, and every currently named test would still pass (the doc:273 test never asserts the survival of a published destination file).
**Consequence:** the one remaining cleanup hazard the task specifically asked about is untested; a plausible implementation regression would ship undetected.
**Fix:** add one AC3a case: Route B (move) crash after step 5, before step 7 — after restart the complete destination file and the `pending` record survive, the missing temp is not an error, and no other file in the folder is touched.

### [MINOR] Route C crash case only covers a half copy, not the complete-but-unmarked file
**Where:** `doc` AC3a (doc:268) vs route C steps 4–5 (doc:239-240).
**Claim:** "Route C, crash na een halve kopie" asserts the half file under the final name is removed at start.
**Reality:** The adjacent window — copy fully finished (step 4) but the `temp_path = NULL` update (step 5) not yet written — is not covered. In that window the file under the final name is complete, yet cleanup (correctly, per doc:250) will still delete it because the record is still `pending` with `temp_path` set. Data-safe (the source still exists, since source deletion follows step 5), but the specified behavior — deleting a complete file — is the exact behavior a test should pin down, since it distinguishes the step-4/step-5 ordering from a swapped order.
**Consequence:** an implementation that writes `temp_path = NULL` before the copy completes would pass all named Route C crash tests while violating the "recorded before bytes are written / cleared only when complete" invariant (doc:216).
**Fix:** add one AC3a case: Route C crash between step 4 and step 5 — after restart the (complete) file under the final name is gone, the source is intact, and the record is `pending`/`interrupted`.

### [MINOR] Deletions are path-based, not identity-based, while NF4 makes an absolute claim
**Where:** `doc` NF4 (doc:213) and Opruimen (doc:249-250) vs the app-file definition (doc:216).
**Claim:** NF4 states a transfer "magaat nooit een bestaand bestand overschrijven of verwijderen dat niet van de app is."
**Reality:** Cleanup and error-time deletion resolve the file by path ("het pad nog als `temp_path` … en alleen als ze nog bestaan", doc:250), not by file identity (`fileResourceIdentifierKey`, which the spec uses elsewhere for folder identity, doc:71). Within the designed threat model — crash, single operator, no concurrent writers to the destination — the property holds. In principle, a foreign process that recreated the exact `temp_path` between the crash and the next start would have its file unlinked by the cleanup.
**Consequence:** none in the actual operating context; the absolute wording of NF4 slightly outruns the mechanism in a corner case outside the threat model.
**Fix:** either capture the file identity at exclusive create (route B step 2 / route C step 2) and verify it at deletion time, or state the assumption (no concurrent writers to destination paths) explicitly. Smallest remedy: document the assumption; no route or test change required.
