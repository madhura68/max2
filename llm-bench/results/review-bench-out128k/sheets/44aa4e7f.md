## Findings

### [MINOR] Route B heading does not explicitly cover same-volume copy
**Where:** `doc` lines 226 (route B heading) and 121-125 (F15).
**Claim:** Route B is titled "kopiëren of verplaatsen tussen volumes, doelvolume mét `RENAME_EXCL`"; route A is same-volume move only; route C is only for destination volumes without the capability.
**Reality:** Same-volume *copy* - the default mode on the default volume, i.e. the app's most common operation - matches no route heading literally and is assigned to route B only by elimination.
**Consequence:** A normative routing table leaves its most frequent case implicit; an implementer could stall or special-case it.
**Fix:** retitle route B "kopiëren (zelfde of ander volume) of verplaatsen tussen volumes" or add one line to F15: copying always follows route B (or C without capability), independent of the volume comparison.

### [MINOR] AC3a retry cases could pass while route B steps 2-4 are repeated
**Where:** `doc` line 231 (route B step 5) and lines 263-265 (AC3a collision cases, three-EEXIST case).
**Claim:** A retry does not repeat route B steps 2-4; the collision cases assert the appeared foreign file is byte-identical, exactly one record, and no pending record.
**Reality:** If an implementation wrongly repeated steps 2-4 on retry, it would create and leak a second `.macsearch-<UUID>.tmp`; the stated assertions would still pass, because the record is updated (not inserted) and the foreign file is untouched. The preamble "de doelinhoud wordt gecontroleerd" (line 257) may or may not catch a stray temp depending on how "doelinhoud" is implemented.
**Consequence:** The exact class of retry-bookkeeping defect fixed in round 4 could slip past AC3a.
**Fix:** in the two final-name collision cases and the three-EEXIST case, explicitly assert the destination folder contains no `.macsearch-*.tmp` (or any other app-owned file) after the case.

### [MINOR] Retry rule references a non-existent record for route C
**Where:** `doc` line 246 (retry rule "route C stap 2") and lines 237-238 (route C steps 2-3), line 218 ("altijd het bestaande record bijgewerkt").
**Claim:** "Bij een herpoging wordt altijd het bestaande record bijgewerkt… Er wordt nooit een tweede record ingevoegd."
**Reality:** In route C an `EEXIST` can only occur at step 2 (the O_EXCL open), i.e. *before* the run's single record is inserted at step 3; bytes are written only after that. So a route C retry always precedes any record, and there is no "existing record" to update.
**Consequence:** Wording inconsistency in a normative invariant; behavior is unambiguous in practice (exactly one record per file), but the "altijd/bestaand" phrasing cannot apply to route C.
**Fix:** state that in route C the retry precedes the (single) record insert, and reword the invariant as "exactly one record per file; retries never insert a second."

### [MINOR] Attempt-counter scope ambiguous for route B UUID collisions
**Where:** `doc` line 217 ("één pogingenteller voor alle botsingen op 'bestaat al'") and line 228 (route B step 2 UUID rotation).
**Claim:** One counter per file covers "alle botsingen op 'bestaat al'" with max 3, then `failed`.
**Reality:** Route B step 2 also handles an "exists already" condition (temp-name collision) by simply choosing a new UUID, apparently unbounded; read literally, the counter sentence could include it.
**Consequence:** Minor ambiguity: an implementation might count UUID collisions against the 3-attempt budget.
**Fix:** specify the counter counts final-name collisions only; UUID rotation in route B step 2 is unbounded.
