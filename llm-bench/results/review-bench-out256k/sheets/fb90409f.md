## Findings

### [BLOCKER] A stored cleanup pathname does not establish ownership of its current occupant

**Where:** `doc`, lines 199–202, 216, 248–251; AC3a at lines 268 and 273.

**Claim:** Cleanup deletes only app-owned files, and other files are never removed.

**Reality:** Ownership is represented by exclusive creation followed by storing `temp_path`. Startup cleanup checks only whether that pathname still exists. A concrete sequence is: route C creates and records `dest_path = temp_path`; the process crashes during copying; another application or the user removes the partial file and places a different file at exactly that pathname; MacSearch restarts. Line 250 directs MacSearch to delete the replacement. The same problem exists for route-B temporary paths. The existing tests preserve a foreign file at a different pathname, so they can pass with this defect intact.

**Consequence:** Restarting MacSearch can delete a foreign file, directly violating NF4 and the binding boundary of the accepted route-C trade-off. This is not an objection to an app-owned partial final file.

**Fix:** Repair the ownership and deletion protocol. Persist an identity for the exclusively created file, distinguish a replacement from that original file, and specify how removal is protected against replacement between validation and deletion. Never unlink solely because a stored pathname exists; preserve mismatches or unverifiable entries. Add crash-recovery tests replacing the file at the exact recorded pathname for both routes B and C, plus coverage of replacement during cleanup.

### [MAJOR] Route C requires updating a record before that record has been inserted

**Where:** `doc`, lines 143–144, 217–218, 235–246; AC3a at lines 265 and 267.

**Claim:** Every retry updates the existing record and resumes route C at step 2; per-file collision handling leaves exactly one action record.

**Reality:** Route C first attempts exclusive creation in step 2 and inserts its first record only in step 3. If a foreign file appears between F16 and that first creation, `open` returns `EEXIST` before any record exists. For different content, line 246 nevertheless requires updating `dest_path` in the existing record. There is no such record. Repeated collisions can also reach the three-attempt limit without an insertion ever occurring. F19b already handles the no-record identical-content case, but there is no corresponding no-record rule for different-content retries or exhausted attempts.

**Consequence:** A normal collision can produce a spurious database failure, missing action history, or implementation-specific behavior inconsistent with the prescribed single-record protocol. The route-C collision test only checks preservation of the foreign file and absence of a rename; it does not catch missing or incorrectly handled records.

**Fix:** Make retry bookkeeping conditional on whether a record exists. Before route C's first successful exclusive creation, retry name selection without attempting a nonexistent-record update; insert the pending record once ownership is established. If processing ends before creation, insert exactly one terminal `skipped_identical` or `failed` record. After insertion, update that same record. Add route-C cases for an initial different-content collision, an identical collision, and three failed exclusive creations, asserting exactly one terminal record and no pending record.

### [MINOR] Route A's collision result contradicts the general suffix result

**Where:** `doc`, lines 131–132, 220–224, and 266.

**Claim:** A different-content conflict resolved with a Finder-style suffix produces `renamed`; route A always updates its record to `moved`, and its collision test expects `moved`.

**Reality:** A same-volume move published under the next suffix satisfies both descriptions, but the result column can hold only one value. The route-A procedure and its acceptance assertion therefore disagree with F16's result rule.

**Consequence:** Implementations can disagree on result classification and summary counts while each follows a different normative passage.

**Fix:** Choose one classification rule and align F16, route A, and AC3a. If suffix publication is classified as `renamed` regardless of mode, use that result in route A when a suffix was selected.
