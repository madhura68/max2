## Findings

### [BLOCKER] Recorded pathname is not persistent proof of ownership

**Where:** source `doc`, lines 196–203, 213–216, 238–250; acceptance cases at lines 268–273.

**Claim:** A file is app-owned after exclusive creation and recording its `temp_path`; crash cleanup deletes an existing file at that recorded path, while never deleting foreign files.

**Reality:** Exclusive creation proves ownership of the object created at that instant, not of every future object at that pathname. For example: route C creates and records the final pathname, writes half the file, and crashes. Before restart, the user or another process removes that partial file and puts an unrelated file at the same final pathname. The run becomes `interrupted`; line 250 then instructs cleanup to delete the unrelated file because the recorded path exists. The schema stores no object identity, and cleanup requires no identity or replacement check. Route B has the same pathname problem for its temporary file. Its successful publication also leaves the old temporary pathname recorded until the result update, so a later replacement at that now-vacant pathname is not app-owned either.

The existing tests leave the foreign file at a different pathname. They can pass with precisely the unsafe cleanup described above.

**Consequence:** Building the specified cleanup produces a direct violation of NF4: deletion of a foreign file. This is independent of, and not justified by, JP's accepted partial-file trade-off.

**Fix:** Repair the ownership/cleanup protocol so a recorded path alone never authorizes deletion. Persist and validate the identity of the created object, conservatively retain files when ownership cannot be established, and account for replacement between validation and deletion rather than adding only a racy pathname check. Clear obsolete cleanup references when publication succeeds. Add restart tests that replace the recorded route B temporary file and route C final file with foreign content, asserting that the replacement survives, plus a replacement-during-cleanup case.

### [MAJOR] Route C invokes existing-record retries before creating a record

**Where:** source `doc`, lines 142–146, 217–218, 235–246; acceptance cases at lines 265–267.

**Claim:** Every retry updates the existing record and never inserts a second one. Route C retries on `EEXIST` at step 2, while inserting its pending record at step 3.

**Reality:** On route C's first `EEXIST`, exclusive creation has failed and step 3 has not run. There is therefore no existing record to update. Nevertheless, the shared retry procedure requires updating that record either to `skipped_identical` or with a new `dest_path`. F19b separately permits inserting an identical-result record when none exists, but NF4's identical branch does not state that exception, and its different-content branch still requires the nonexistent record. The three-collision exhaustion path also needs to produce a single terminal action despite never having reached route C's insert step.

AC3a's route C collision case checks foreign content and rename calls, but does not require exactly one terminal action, no pending action, and the expected result. Consequently it can pass while this bookkeeping gap remains.

**Consequence:** An implementer must invent an exception to the normative retry procedure. Following it literally can leave route C collisions unlogged or mishandled, defeating the advertised single-record fix and requiring rework.

**Fix:** Specify route C's pre-creation retries separately: while no record exists, recompute candidates without updating a nonexistent action; insert exactly one terminal action on identical content or exhausted retries, or insert exactly one pending action after successful exclusive creation. Keep the existing-record retry rules for routes A and B. Extend route C tests with different-content success, identical-content skip, and three `EEXIST`s, each asserting exactly one terminal record and no pending record.
