## Findings

### [BLOCKER] A recorded pathname does not prove ownership of the file deleted during cleanup

**Where:** Source `doc`, NF4 ownership and cleanup, lines 213–216 and 248–250; route B lines 228–233; route C lines 237–240; AC3a lines 268–273; schema lines 196–203.

**Claim:** A transfer never deletes an existing file that is not the app's; crash recovery deletes only app-owned files identified by their recorded `temp_path`.

**Reality:** The database records a path, not the identity of the exclusively created object. For example: route C creates and records `/dest/name.jpg`, writes half the data, and crashes. Before the next start, another process removes that partial file and places a foreign file at `/dest/name.jpg`. The prescribed startup cleanup sees an existing recorded path and deletes the foreign file. Route B has a related window: after publication, its old temporary pathname remains recorded; a foreign file created at that now-free pathname can be deleted after a crash. Exclusive creation does not reserve a pathname indefinitely. The existing tests preserve foreign files at different names, so they can pass with this defect present.

**Consequence:** Implementing the stated cleanup algorithm violates the binding prohibition on deleting foreign files. This is separate from the accepted half-written-final-file trade-off: the defect is deletion of a replacement file that the app never owned.

**Fix:** Repair the ownership and deletion protocol so ownership is tied to the created object, not merely its former path. Persist an appropriate object identity, and specify how replacement is prevented or safely handled during deletion; a path-based identity check followed by an unprotected unlink still has a race. If ownership cannot safely be established, leave the file in place and report it rather than delete it. Add replacement-at-the-recorded-path tests for route C and route B, including replacement before startup cleanup and during cleanup.

### [MAJOR] Route C requires retry updates before its record exists

**Where:** Source `doc`, F19b lines 142–146; NF4 general retry rule lines 217–218; route C lines 235–246; AC3a lines 265–267.

**Claim:** Every retry updates the existing record, never inserts a second record, and terminates with one correctly finalized action record.

**Reality:** Route C step 2 performs exclusive creation before step 3 inserts the record. An `EEXIST` at step 2 therefore occurs with no record and no owned file. The retry instructions nonetheless require updating `dest_path` in the existing record before returning to step 2. There is no such record. F19b explicitly handles the no-record case for `skipped_identical`, but there is no equivalent rule for a different-content retry or exhaustion of three collisions. The route C collision test only asserts preservation of the foreign file and absence of a rename against it; an implementation that fails the transfer immediately or loses its action record could satisfy those assertions.

**Consequence:** The new route is not consistently implementable as written. Implementers must invent bookkeeping behavior, and a normal destination-name race can cause a failed or unlogged transfer rather than the required suffix retry.

**Fix:** Explicitly distinguish retries before and after record creation. For route C before successful exclusive creation, repeat name selection and creation without updating a nonexistent row; insert exactly one terminal action for an identical-content skip or exhausted retry, or insert the pending row after successful creation as currently specified. Preserve the existing-record rule once a row exists. Extend route C tests to assert successful different-content retry, identical-content skip, three-collision failure, exactly one action row, and no remaining pending row after normal completion.
