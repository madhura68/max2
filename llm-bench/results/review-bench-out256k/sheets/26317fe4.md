## Findings

### MINOR 1: Ambiguity — 3rd `EEXIST` with identical content

**Where:** NF4 "Algemeen" (line 217) vs "Herpoging na `EEXIST`" (lines 243–246).

**Claim:** The general rule says after 3 attempts the result is `failed`. The retry rules say identical content → `skipped_identical`.

**Reality:** On the 3rd `EEXIST`, it is unclear which rule takes precedence. If the 3rd `EEXIST` file has identical content, should the result be `failed` (counter exhausted) or `skipped_identical` (content matches)? The AC3a test "Drie keer `EEXIST`: het resultaat is `failed`" (line 265) covers only the all-different case and does not resolve this.

**Consequence:** An implementer could choose either interpretation. Both are safe (no data loss), but divergence could cause rework if a reviewer expects the other.

**Fix:** Add a sentence in the retry rules: "De pogingenteller geldt ook voor identieke inhoud; bij de 3e `EEXIST` is het resultaat altijd `failed`, ongeacht of de inhoud identiek is." Or the reverse: "Identieke inhoud op de 3e `EEXIST` geeft `skipped_identical`; de pogingenteller stopt alleen bij verschillende inhoud."

---

### MINOR 2: Non-`EEXIST` error handling is implicit in route-specific steps

**Where:** Route A step 3 (line 223), route B step 5 (line 231), route C step 2 (line 237).

**Claim:** Each route step mentions only `EEXIST` handling.

**Reality:** Errors other than `EEXIST` (e.g. `EACCES`, `EIO`, `ENOSPC`) are covered only by the general NF4 cleanup rule ("Bij een fout: de app verwijdert alleen het eigen bestand (`temp_path`) en de bron blijft staan", line 249). The route-specific descriptions do not reference this fallback.

**Consequence:** An implementer reading only the route steps might miss the general cleanup rule or implement different error handling per route, leading to inconsistent behavior.

**Fix:** Add to each route step: "Bij een andere fout dan `EEXIST` geldt de algemene foutafhandeling (eigen bestand verwijderen, bron intact, resultaat `failed`)."

---

### MINOR 3: Route A and B crash recovery untested

**Where:** AC3a (lines 257–273).

**Claim:** AC3a covers crash safety for `FileTransfer`.

**Reality:** Crash recovery tests exist only for route C ("crash na een halve kopie", "crash na `temp_path = NULL`", "Opruimen na een crash", lines 268–273). Route A has crash windows between record insert and `renamex_np` (step 2→3) and between rename and record update (step 3→4). Route B has crash windows between temp file creation and record insert, and between `renamex_np` and record update. None of these are tested.

**Consequence:** A defect in route A or B crash recovery (e.g. a pending record with a stale `dest_path` causing confusion) could go undetected. The practical risk is low because route A is atomic and route B uses `RENAME_EXCL`, but the coverage gap is real.

**Fix:** Add two test cases: (a) route A crash after `renamex_np` succeeds but before record update → file at dest, no data loss; (b) route B crash after `renamex_np` succeeds but before record update → temp file gone (renamed), file at dest, no stale temp file.

### MINOR 4: F14 keyword-mapnaam wording vs §1a

**Where:** F14 (line 118) vs §1a (line 30).

**Claim:** §1a says the destination is `<bestemming>/<keyword zoals ingetypt>/...`. F14 derives `keyword-mapnaam` from the typed input by applying sanitization (trimming, whitespace collapsing, `/` and `:` → `-`).

**Reality:** For keywords containing `/` or `:`, the folder name differs from what a literal reading of §1a would produce. The sanitization is filesystem-necessary and the intent is clear, but the wording in §1a could mislead someone implementing directly against it without reading F14.

**Consequence:** Minor documentation inconsistency; no functional impact since the sanitized form is the only filesystem-viable option.

**Fix:** In §1a, add a parenthetical: "<keyword zoals ingetypt, gesaneerd voor bestandssysteem volgens F14>" or add a footnote cross-referencing F14.

---

### MINOR 5: Route C — crash between copy-complete and `temp_path = NULL` deletes a complete file

**Where:** Route C step 4→5 (lines 239–240) with NF4 cleanup (line 250).

**Claim:** After a crash, only half-written app-owned files under the final name are cleaned up.

**Reality:** If the copy in route C step 4 completes successfully but the app crashes before step 5 (`temp_path = NULL`), the record still has `temp_path = dest_path`. At startup cleanup, this **complete** file is deleted alongside any half-written files. The source is intact (step 6 hasn't run yet), so no permanent data loss occurs, but the copy work is wasted. The AC3a test covers the half-copy case (line 268) but not the complete-copy-before-NULL case.

**Consequence:** A wasted copy on a very unlucky crash timing. Acceptable given the accepted trade-off, but the text should acknowledge that the cleanup is conservative (deletes complete files too) rather than implying it only deletes half-written files.

**Fix:** In NF4 "Opruimen" (line 250), add: "Omdat de app niet kan weten of een bestand half of volledig is geschreven, verwijdert de opruiming elk bestand met een `temp_path` in een `pending`-record, ook als de kopie voltooid was vóór de crash."
