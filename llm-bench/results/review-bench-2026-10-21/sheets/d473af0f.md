## Findings

### [MINOR] 1. The retry rule speaks of "the existing record" for route C, which has none at that point
**Where:** NF4 lines 237 and 243–246, and F19b line 143.
**Claim:** After an `EEXIST`, the existing record is updated, and an identical result sets that record to `skipped_identical`.
**Reality:** In route C the `EEXIST` occurs at step 2, before the pending insert at step 3. No record exists yet. F19b says that in this case a record is inserted directly. The retry text therefore applies literally only to routes A and B.
**Consequence:** An implementer could add a pointless "find the record" step, or insert two records. The AC3a assertion "exactly one record" catches the second error, but the text is ambiguous.
**Fix:** Add one sentence to the retry rules: "if no record exists yet (route C, or F16 chose `skipped_identical` before any insert), insert it with the new `dest_path`/result; otherwise update it."

### [MINOR] 2. The crash tests can pass when they only exercise the error path
**Where:** AC3a lines 268–269 and 273.
**Claim:** "Route C, crash after a half copy: after the start the half own file is gone."
**Reality:** The tests use a `FileOps` with error injection. An injected error triggers "Opruimen bij een fout" (line 249). That path deletes the own file during the run, so the test passes even if the cleanup at app start (line 250) is missing. Only the last AC3a bullet (line 273) tests the start cleanup, and it uses a hidden `.macsearch-*.tmp` file. It does not cover a route C final-name `temp_path`.
**Consequence:** A bug that deletes the wrong path, or that never deletes it, in the start cleanup for route C can go undetected.
**Fix:** State that the crash cases simulate the crash without running the error-path cleanup. For example, the injection stops the batch and leaves the files and records as they are, and then the startup routine runs on a fresh `HistoryStore`. Extend the line 273 test with a route C case where `temp_path == dest_path` and the foreign neighbour keeps its content.

### [MINOR] 3. Route C is tested less than routes A and B
**Where:** AC3a lines 262–273.
**Claim:** Route C has the same safety as the other routes.
**Reality:** Cases are missing for route C:
- an identical collision (`skipped_identical`, one record, no leftovers);
- three times `EEXIST`;
- a size mismatch on a move (the own final-name file must be removed and the source kept);
- a failed source delete (`copied` plus a warning).

The line 267 assertion "a `rename` is never called" cannot be observed on the real `FileOps`, which line 257 requires for these cases. Route A also has no identical-collision case.
**Consequence:** The route C tail (steps 4–6) is the newest code and the likeliest place for a defect.
**Fix:** Run the existing generic cases (collision identical, 3×`EEXIST`, size mismatch, source delete fails) parametrised over both capability values. For the "never rename" assertion, use a counting wrapper around the real `FileOps`.

### [MINOR] 4. A failing intermediate record update is not specified
**Where:** F19b lines 143–150 and NF4 route C step 5 (line 240), and the matching `temp_path` update in route B.
**Claim:** F19b regulates the insert failure and the final result update.
**Reality:** The `temp_path = NULL` update (route C step 5) is a third write. Its failure is not covered. The same applies to the `dest_path` update during a retry.
**Consequence:** Behaviour is undefined. The safe choice (stop, keep the source, remove the own file) follows from line 249, but a failed update on an `aborted` run is never cleaned up by line 250, which only handles `interrupted` runs. In route C the pending record keeps `temp_path = dest_path`, so a later cleanup of an `interrupted` run could delete a complete file. In a move that is safe only because the source is still present.
**Fix:** Add a line: "If an intermediate update fails, handle it as an error: delete the own file, keep the source, result `failed`, batch stops as in F19b step 1." Make sure the source is never deleted before the `NULL` update has succeeded.

### [MINOR] 5. Capability query path and volume-boundary edge cases are unspecified
**Where:** F15 lines 122–125.
**Claim:** The capability is determined once per run for the destination volume.
**Reality:**
- It is not stated on which path to query. It should be the created destination folder, not `dest_root`.
- It is not stated what happens when route A's `renamex_np` returns `EXDEV` (APFS firmlinks or a volume-identifier quirk), or `ENOTSUP`/`EINVAL` despite the capability flag.
- SMB servers may report the flag and still reject it.

The literal text gives `failed` for these cases, which is safe.
**Consequence:** A rare failed file, not data loss.
**Fix:** Add one sentence: query on the created destination folder. `EXDEV` on route A falls back to route B. `ENOTSUP`/`EINVAL` from `renamex_np` marks the run as capability absent and continues with route C for the next files. Never fall back to a plain `rename`.

### [MINOR] 6. Durability of the `temp_path = NULL` ordering is not stated
**Where:** NF4 route C step 5 (line 240) and cleanup (line 250).
**Claim:** A complete file is never cleaned up, because the `NULL` update precedes the source delete.
**Reality:** The ordering holds for an app crash. After power loss with a relaxed SQLite `synchronous` setting (WAL with `NORMAL`), a committed `NULL` update can be rolled back while the source delete is already persistent. Cleanup would then delete the complete copy whose source is gone.
**Consequence:** A theoretical loss for a single-user app after a power failure. GRDB's default does not set `NORMAL`, but the spec does not say so.
**Fix:** Add one line in §2: do not weaken `synchronous` below `FULL` (the SQLite default). Optionally add an `F_FULLFSYNC` on the destination fd before the `NULL` update.

## Other checks, no finding
- **AppleDouble `._` files on exFAT/SMB.** `fcopyfile(COPYFILE_ALL)` writes xattrs as `._name` sidecars on volumes without native xattrs. AC7's "no stray files" assertion mentions only `.macsearch-*.tmp`. macOS removes the sidecar on `unlink`, and the scanner skips hidden files, so this is not a finding. It is worth knowing during the AC7 exFAT proof.
- **NF4 against F0d.** Stop finishes the current file, including the route C tail, before stopping. That is consistent.
- **F16 against route C.** F16's candidate check happens before the `O_EXCL` create, and `EEXIST` re-enters F16. This is consistent. An empty file left by a crash (line 251) is seen as "different content" and gets the suffix. That is acceptable under the accepted trade-off.
