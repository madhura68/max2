## Findings

### [MAJOR] Recorded pathname does not prove that the file being cleaned up is still app-owned

**Where:** Source `doc`, NF4 ownership and cleanup, lines 213–216 and 248–251; schema lines 199–203; AC3a lines 268 and 273.

**Claim:** A transfer never deletes a foreign file. On restart, cleanup deletes existing paths recorded as `temp_path` in pending actions.

**Reality:** The record stores a pathname, not the identity of the exclusively created file. A concrete route C sequence is: create destination D exclusively, record D as `temp_path`, write half the data, and crash. Before restart, another application or the operator removes that partial file and puts a different file at D. The specified startup cleanup checks only that D exists and deletes the foreign replacement. Route B has the same problem at its temporary pathname. It also leaves `temp_path` recorded after successful publication, creating another opportunity for that old pathname to be occupied by an unrelated file before crash recovery. The tests protect a foreign file at a different pathname, which does not exercise this failure.

**Consequence:** Implementing cleanup literally violates the binding prohibition on deleting a file that is not the app's. Accepting partial app-owned files after a crash does not accept deleting their foreign replacements.

**Fix:** Repair ownership tracking and cleanup together: persist a verifiable identity of the exclusively created object, distinguish publication/completion from incomplete ownership, and specify a cleanup protocol that cannot delete a substituted object. A pathname alone must never authorize deletion; if ownership cannot safely be established, retain the file and report it rather than deleting it. Account for substitution between validation and deletion, not just a one-time existence check. Add restart tests replacing the recorded route B and route C pathname with a foreign file and assert that its bytes survive.

### [MAJOR] Route C's first EEXIST retries a database record that does not exist

**Where:** Source `doc`, F19b line 143; NF4 lines 218, 235–246; AC3a lines 265 and 267.

**Claim:** A retry always updates the existing record, never inserts a second record, and resumes route C at exclusive creation.

**Reality:** Route C first attempts `open(O_CREAT|O_EXCL|O_WRONLY)` in step 2 and inserts its pending record only in step 3. If another process creates the chosen destination between F16 and step 2, the first open returns EEXIST and there is no action record. The non-identical retry branch nevertheless requires updating `dest_path` in the existing record. F19b explicitly handles an absent record for `skipped_identical`, but no equivalent rule exists for this different-content branch. If an implementer creates a record during that retry to satisfy the update requirement, route C step 3 subsequently instructs another insert, contradicting the one-record rule. The route C collision test checks preservation of the foreign file and absence of unsafe rename, but not successful completion, one action record, or absence of pending records.

**Consequence:** A normal, expressly anticipated destination collision has no consistent executable bookkeeping sequence. An implementation must invent behavior, fail the transfer unnecessarily, or risk missing/duplicate action records.

**Fix:** Distinguish retries before record creation from retries after it. For route C EEXIST before a successful exclusive open, advance F16 and the attempt counter without updating a nonexistent record. After successful creation, insert the pending record exactly once before copying bytes. Specify terminal logging for exhausted pre-creation attempts. Extend the real-FileOps route C collision and exhaustion tests to assert the expected result, source/destination contents, exactly one action record, and no pending record after normal completion.

### [MINOR] Same-volume suffix moves have conflicting result requirements

**Where:** Source `doc`, F16–F17 lines 131–132; NF4 route A line 224; AC3a line 266.

**Claim:** F16 assigns `renamed` when different content requires a Finder-style suffix. Route A always writes `moved`, and its collision acceptance test explicitly expects `moved` under a subsequent free name.

**Reality:** A same-volume move to `name (2).ext` satisfies both descriptions, but the schema allows only one result value. The normative requirements and acceptance test therefore disagree about its recorded result.

**Consequence:** The implementation and summary can classify the same successful action differently depending on which section is followed.

**Fix:** State one precedence rule for suffix transfers and apply it consistently to route A and its acceptance test. No additional result type is necessary.
