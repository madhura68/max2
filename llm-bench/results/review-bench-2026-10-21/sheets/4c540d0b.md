# IDEA-263 MacSearch spec r5 — round 5 review

## Verification of the round-4 fixes (against r5 itself, not the change list)

**Fix 1 — no overwrite fallback: held.** NF4 (doc:213-251) has exactly three routes. Route A (doc:220-224) is `renamex_np(src, dest, RENAME_EXCL)` for same-volume moves. Route B (doc:226-233) is an exclusive `.macsearch-<UUID>.tmp` (doc:228), a pending record, `fcopyfile` + explicit dates (doc:230), then `renamex_np(temp, dest, RENAME_EXCL)` (doc:231). Route C (doc:235-241) creates the final name itself with `open(O_CREAT|O_EXCL|O_WRONLY)` (doc:237) on volumes without the capability, for both copy and move. The capability is probed once per run via `getattrlist` `VOL_CAP_INT_RENAME_EXCL` (doc:123). A search of the whole document finds no plain `rename` anywhere; route C never renames onto a foreign name at all. The only files the app ever deletes are (a) paths it created exclusively and recorded as `temp_path` (doc:250), and (b) the source after a verified move — so the mechanism never overwrites or deletes a foreign file. All named APIs exist on current macOS (`renamex_np`/`RENAME_EXCL`, `VOL_CAP_INT_RENAME_EXCL` via `getattrlist`, `fcopyfile`/`COPYFILE_ALL`, `open(O_EXCL)`).

**Fix 2 — retry bookkeeping: held.** One attempt counter, max 3, per file (doc:217); a retry always updates the existing record, never inserts a second one (doc:218); route B's retry continues at step 5 and reuses the temp, explicitly not repeating steps 2-4 (doc:231); a retry ending in identical content deletes the own file and sets the record to `skipped_identical` (doc:245); AC3a asserts "precies één record" and "geen pending-record meer" for both final-name collision cases and the three-EEXIST case (doc:263-265).

**Fix 3 — metadata: held.** Both dates set explicitly (doc:230, doc:239), F15 states preservation with a warning on failure (doc:126), and AC3a has a success and an injected-failure case (doc:271-272).

**Fix 4 — folder creation: held.** F14 places folder creation after the `search_run` insert and before the first file, with `aborted` on failure (doc:120); AC4 has the matching case (doc:283).

**Fix 5 — tests: held.** AC3a (doc:257-273) contains both final-name collision cases (doc:263-264), three EEXISTs (doc:265), a route A collision (doc:266), and route C cases with injected capability: collision (doc:267), crash after a half copy (doc:268), and crash after `temp_path = NULL` (doc:269), plus cleanup not touching a foreign `.macsearch-other.tmp` (doc:273).

**Crash windows, per route (no defect found, recorded as evidence):** Route A: a crash between the rename (doc:223) and the record update (doc:224) leaves a pending record with `temp_path = NULL` — nothing to clean, source gone, file present, run `interrupted` (F19c, doc:152). Route B: a crash after publication leaves `temp_path` pointing at a no-longer-existing temp; cleanup deletes "alleen als ze nog bestaan" (doc:250), so the published file survives. Route C: `temp_path = NULL` is written before the source is deleted (doc:240), so a complete file whose source is gone never carries a `temp_path` — cleanup cannot delete it. The source is deleted only after the `temp_path = NULL` write succeeds, so a failed/crashed update always leaves the source intact.

**Necessity:** none removable. Route B exists to keep NF4's guarantee that a RENAME_EXCL volume never holds a half-written file under the final name (doc:213); route C exists because of the binding JP decision of 2026-10-16; the counter and retry rules guard the one-record invariant. Collapsing routes A/B into C would drop an agreed protection.

## Findings

### [MINOR] Retry rules presuppose a record that route C's first EEXIST cannot have yet
**Where:** `sources/doc:243-246` (Herpoging), `sources/doc:237-238` (route C steps 2-3), `sources/doc:218`, `sources/doc:143` (F19b).
**Claim:** "Bij een herpoging wordt altijd het bestaande record bijgewerkt" (doc:218) and "dest_path in het bestaande record wordt bijgewerkt" (doc:246).
**Reality:** In route C the only EEXIT point is step 2 (doc:237), which precedes the record insert at step 3 (doc:238). A first-attempt EEXIST therefore retries with no existing record; only F19b's "Bestaat er nog geen record, dan wordt er direct een record ingevoegd" (doc:143) covers that path, and the Herpoging section contradicts it by always speaking of "het bestaande record". Route A (record at doc:222, rename at doc:223) and route B (record at doc:229, EEXIST at doc:231) do always have a record when they retry.
**Consequence:** Implementer ambiguity on route C's first collision; AC3a's "precies één record" bounds the damage but the spec text alone points two ways.
**Fix:** Add one sentence to the Herpoging block: "Bestaat er nog geen record (route C, eerste EEXIST), dan wordt direct een record ingevoegd (F19b)."

### [MINOR] Attempt-counter scope is undefined against F16's candidate scan
**Where:** `sources/doc:217` (counter), `sources/doc:131` (F16 candidates), `sources/doc:228` (route B step 2).
**Claim:** "Per bestand is er één pogingenteller voor alle botsingen op 'bestaat al': maximaal 3" (doc:217); F16 tests candidates "(2), (3), …, tot en met de eerste vrije naam" (doc:131).
**Reality:** The document never says whether F16's per-candidate existence probes, or route B step 2's temp-UUID collision (doc:228), consume the counter. If they do, F16's unbounded scan is effectively capped at 3 candidates; if they do not, F16 must use non-consuming existence checks, which the document also never states.
**Consequence:** With two occupied candidates plus one race (or a literal reading of "alle botsingen"), a transfer can end `failed` although a free name exists — a safe degradation that contradicts F16 and that no AC case exercises (AC3's `(2)`/`(3)` case needs at most one collision).
**Fix:** One clause in NF4: only failed exclusive creations/publications consume the counter; F16 probes and UUID retries do not.

### [MINOR] NF4's blanket cleanup promise vs the record-less empty residual file
**Where:** `sources/doc:213` vs `sources/doc:251`.
**Claim:** NF4's introduction: a half-written app file under the final name on a no-capability volume "wordt bij de volgende start opgeruimd" (doc:213).
**Reality:** The accepted-residual bullet (doc:251) discloses that a crash between the exclusive create (route C step 2) and the record insert (step 3) leaves a 0-byte file under the final name with no record — and cleanup is bound to pending records' `temp_path` (doc:250), so that file is never removed by any mechanism. The residual bullet describes it but does not reconcile it with the introduction's promise, nor say what the next attempt does with it.
**Consequence:** A stray empty file under the final name survives every restart and forces a spurious `(2)` suffix on the next attempt (F16 sees a size mismatch). This is adjacent to, but narrower than, the JP-accepted trade-off, which is why it is MINOR and not raised as a defect of the trade-off itself.
**Fix:** One clause at doc:251: "dat lege bestand blijft staan en wordt bij een volgende poging als een gewone botsing behandeld (F16)."

### [MINOR] A failed `temp_path = NULL` update causes cleanup to delete a completed file
**Where:** `sources/doc:240` (route C step 5), `sources/doc:250` (cleanup), `sources/doc:145-146` (F19b rule 2).
**Claim:** F19b rule 2: a failed update leaves the pending record standing; cleanup deletes files whose path is still a pending record's `temp_path`.
**Reality:** If route C's `temp_path = NULL` write fails (database error) after a fully successful copy, the record still names the complete destination file as `temp_path`, so the next start's cleanup deletes it. The source is intact (deletion is gated on the update, doc:240), so no data is lost.
**Consequence:** A successful transfer is silently undone and must be redone. Safe, but unacknowledged.
**Fix:** Acknowledge the case in F19b/NF4, or let the failed-update path also clear `temp_path` before stopping.

### [MINOR] The "three EEXIST" test case names no route
**Where:** `sources/doc:265`.
**Claim:** The case asserts "het resultaat is failed, het eigen bestand is weg, de bron is intact en er is precies één record".
**Reality:** Only route B can have an own file when an EEXIST occurs (route C's EEXIST at doc:237 precedes ownership), so the case as worded is satisfiable only by route B; counter exhaustion inside route C (three raced `O_EXCL`s on the final name) is untested.
**Consequence:** Route C's attempt-counter path could be implemented wrong (e.g. unlimited) without failing AC3a, since the route C collision case (doc:267) exercises only one collision.
**Fix:** Add "(route B)" to doc:265 and either a route C variant or a note that route C's counter is exercised by the same logic.

### [MINOR] `skipped_identical` on retry does not clear `temp_path`
**Where:** `sources/doc:245`.
**Claim:** The identical-content retry rule deletes the own temporary file and updates the record to `skipped_identical`.
**Reality:** It does not say `temp_path` is set to `NULL` (the data model's "NULL = niets op te ruimen", doc:201). Harmless in practice because cleanup checks existence (doc:250), but the invariant "`temp_path` ⇔ own incomplete file to clean" is left implicit, and the one-record test does not inspect `temp_path`.
**Consequence:** A lax implementation leaves a dangling `temp_path` on a final record; no current test would catch it.
**Fix:** One clause at doc:245: "…en `temp_path` wordt `NULL`."

### [MINOR] Unobservable assertion in the route C collision case
**Where:** `sources/doc:267`.
**Claim:** "Er wordt nooit een `rename` aangeroepen op een doelnaam die van een ander is."
**Reality:** The collision cases run on the real `FileOps` (doc:257), on which individual calls cannot be spied; the byte-for-byte check on the foreign file is the only observable assertion of the named defect.
**Consequence:** The sentence reads as a call-level assertion that the test cannot actually make; an implementation using a plain rename onto a free-but-checked name would still pass on outcome alone in some orders.
**Fix:** Reword to the observable outcome (foreign file byte-identical, own result correct, one record) or state that a spy wraps the real `FileOps`.

Fixes 1-5: all held. Nothing is removable without losing agreed acceptance or protection. **GO**.
