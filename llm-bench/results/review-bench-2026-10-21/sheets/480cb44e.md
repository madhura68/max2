### Findings

#### [MAJOR] Route C retry never updates `temp_path`; it can be left pointing at a foreign file
- **Where:** `doc` L218 (Algemeen: "Bij een herpoging wordt altijd het bestaande record bijgewerkt (dest_path, resultaat)"), L243–246 (Herpoging na EEXIST: "dest_path in het bestaande record wordt bijgewerkt en de app gaat verder bij … route C stap 2"), vs. route C step 3 at L238.
- **Claim:** A retry always updates the existing record, and the retry section enumerates `dest_path` (and result) as what changes.
- **Reality:** Route C is the only route where `temp_path == dest_path`. Both retry statements (L218 and L246) omit `temp_path`. The rule that ties `temp_path` to the newly created exclusive file exists only in the insert-case wording of route C step 3 (L238: "met dest_path gelijk aan temp_path, gelijk aan dit bestand"). On a retry with different content, the literal reading of L246 is: update `dest_path`, create a new `O_EXCL` file at the new name, copy bytes into it, and only set `temp_path = NULL` at step 5 — so during the whole retried copy the pending record's `temp_path` still names the foreign file from the first `EEXIST`.
- **Consequence:** (a) It violates NF4's own definition of "van de app" (L216): the new file's `temp_path` is not recorded before bytes are written, so a crash mid-retry leaves the app's own half-written file unrecorded and undeletable by cleanup. (b) Worse, the crash cleanup rule (L250: delete whatever path still stands as `temp_path` in a pending record) then deletes the **foreign** file at the old collided name — the single action JP explicitly forbade, and the exact thing this round was asked to verify. The AC3a route C cases (L267–269) test the initial pass and crashes, not the retry path, so this would not be caught.
- **Fix:** Repair, one sentence. In the Herpoging section (and in the L218 bullet): "Op een herpoging in route C worden bij het bijwerken van het bestaande record zowel `dest_path` als `temp_path` op het nieuw exclusief aangemaakte bestand gezet, vóór er bytes in worden geschreven."

#### [MINOR] Same-volume copy with `RENAME_EXCL` has no route
- **Where:** `doc` L226 ("Route B: kopiëren of verplaatsen **tussen volumes**, doelvolume mét RENAME_EXCL"), L220 (route A is move-only), L235 (route C requires *no* capability).
- **Claim:** The three routes cover every combination of operation, volume relation and capability.
- **Reality:** A copy on the same volume as the destination, on a volume that does have `RENAME_EXCL` (the ordinary APFS case), matches no route header: A is move-only, B says "tussen volumes", C requires the capability to be absent.
- **Consequence:** An implementer may route same-volume APFS copies through route C, which would break NF4's guarantee (L213) that on `RENAME_EXCL` volumes a half-written file never appears under the final name; or they guess route B. No wrong data outcome, but the normative routing table has an empty cell.
- **Fix:** Repair — reword the route B header to "elke kopie, en verplaatsen tussen volumes, doelvolume mét `RENAME_EXCL`".

#### [MINOR] AC3a route C collision case asserts only the foreign file's integrity
- **Where:** `doc` L267.
- **Claim:** The route C collision case covers the no-overwrite behavior.
- **Reality:** It asserts only "het verschenen bestand is ongewijzigd" and "Er wordt nooit een `rename` aangeroepen op een doelnaam die van een ander is". Unlike its siblings (L263: "precies één record en er is geen pending-record meer"; L265: "precies één record"), it states no expected result value and no record assertions.
- **Consequence:** The test as described can pass while the transfer ends in the wrong result or leaves a stale pending record — i.e. while the bookkeeping defect is present.
- **Fix:** Repair — add to L267 the same assertions as L263/L265: expected result, "precies één record", "geen pending-record meer".

#### [MINOR] Identical-collision regression test does not pin the record's state
- **Where:** `doc` L264.
- **Claim:** This case is the regression test for round-4 MAJOR #2 (stale pending record after an identical-content retry).
- **Reality:** It says "Het resultaat is skipped_identical, er is precies één record en het tijdelijke bestand is weg", but unlike L263 it never states that no pending record remains / that the single record's result is `skipped_identical` rather than `pending`.
- **Consequence:** If "precies één record" is checked only as a count and the result is read from the API return rather than the database, the original defect (record left on `pending`) could recur and the test would still pass.
- **Fix:** Repair — mirror L263: "… er is precies één record met resultaat `skipped_identical` en er is geen pending-record meer."

#### [MINOR] Result value for suffixed outcomes is inconsistent and partly unspecified
- **Where:** `doc` L131 (F16 labels the suffix outcome `renamed`), L263 (copy with collision → `renamed`), L266 (route A move with collision → `moved`), L132 (F17 result set).
- **Claim:** F17's result set is well-defined for every outcome.
- **Reality:** A copy that lands under `naam (2).ext` is `renamed` (L263), a route A move under a suffix is `moved` (L266) — but for a move via route B or C that ends under a suffix the spec states no value (`moved`? `renamed`?), and F16's `renamed` label cuts across the mode-based values of F17.
- **Consequence:** Ambiguous summary and history entries; an implementer must invent the mapping.
- **Fix:** Repair — one sentence in F16/F17 fixing the mapping, e.g. "het resultaat volgt de modus (`copied`/`moved`); het feit dat er een suffix is gekozen staat in `error` of een eigen veld" — or state that `renamed` replaces the mode value whenever a suffix was needed, for all routes.

#### [MINOR] Route C window around the `temp_path = NULL` write has two undocumented outcomes
- **Where:** `doc` L240 (step 5), L250 (cleanup), L151–153 (F19c: cleanup only for runs that become `interrupted`).
- **Claim:** The accepted residual risk is only the create-before-insert window (L251).
- **Reality:** Two further outcomes of a crash or failed write at step 5 are not covered: (a) a crash after the copy completes but before the `temp_path = NULL` write leaves a **complete** app-owned file at the final name that startup cleanup then deletes (source still exists, so no data loss, but a finished copy silently disappears); (b) if the step-5 update fails gracefully, the run goes to `aborted`, which is outside the `interrupted`-only cleanup scope, so a pending record with a live `temp_path` pointing at a complete file stays forever.
- **Consequence:** Undocumented behavior at exactly the boundary the spec is otherwise precise about; no unsafe action either way.
- **Fix:** Repair — extend L251 with these two windows and their accepted outcomes (either document that a complete-but-unrecorded route C file may be deleted at restart, or extend cleanup to aborted runs with the same pending-`temp_path` rule).
