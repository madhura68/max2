## Findings

### [MINOR] Crash cleanup deletes by path, without checking file identity
**Where:** NF4 'Opruimen — Na een crash' (line 250); route C step 3 (line 238); the NF4 absolute claim (line 213).
**Claim:** Cleanup 'only deletes files whose path is still stored as `temp_path`, and only if they still exist'. NF4 says a file that is not the app's is never deleted.
**Reality:** The check is by path only. In route C that path is the user-visible final name. Between the crash and the next start, a user or another tool could delete or replace the half file with a different file under the same name. Cleanup would then delete that foreign file. The record holds no inode, `fileResourceIdentifier`, size or timestamp to tell the two apart.
**Consequence:** The 'never deletes a foreign file' guarantee has a hole. It needs an external actor in a narrow window, hence MINOR.
**Fix:** Store the file identity (`fileResourceIdentifierKey` or inode) in the pending record at insert time, which is possible because the fd is already open. Have cleanup delete only on an identity match. A cheaper alternative is to require a creation date at or after `search_run.created_at` and a size at or below the source size. Add one AC3a case: a foreign file replaces the half file, and after the start it is unchanged.

### [MINOR] Failure of the `temp_path = NULL` update (route C step 5) is unspecified
**Where:** Route C step 5 (line 240); F19b step 2 (lines 145–146).
**Claim:** The record is updated with `temp_path = NULL` and only then is the source deleted.
**Reality:** F19b only covers a failed insert and a failed final update. If the NULL update fails, the file is complete but the record still has `temp_path = dest_path`. The spec does not say whether the source is kept or whether the batch stops with `aborted`. Cleanup only runs for `interrupted` runs. If the `aborted` write also fails, the run becomes `interrupted` and the complete file is deleted. The source still exists in that case, provided it was not deleted. The sequencing 'only after' implies this but does not state it.
**Consequence:** An implementer has to guess. The risk of losing the only copy of a file is low but present if the source delete runs anyway.
**Fix:** Add one sentence: if the NULL update fails, do not delete the source, treat it like a failed update in F19b step 2 (stop, `aborted`), and add an AC3a case with injection.

### [MINOR] Route C retries and a `failed` outcome have no record to update
**Where:** F19b step 1 (line 143); NF4 'Herpoging' (lines 243–246); route C steps 2–3 (lines 237–238); AC3a 'Drie keer EEXIST' (line 265).
**Claim:** A retry always updates the existing record, and the 3-EEXIST test asserts exactly one record.
**Reality:** In route C, EEXIST happens in step 2, before the record is inserted in step 3. The retry rule 'update the existing record' therefore does not apply there. F19b only describes a direct insert for `skipped_identical`. A `failed` outcome with no pending record is not described. That covers three EEXISTs in route C and an unreadable source before the insert (AC3, 'onleesbaar bestand').
**Consequence:** The record count and the audit trail for these failures are underspecified. The 'exactly one record' assertion cannot be implemented unambiguously for route C.
**Fix:** State in F19b that an outcome without an existing record (`skipped_identical` or `failed`) is inserted directly, with `dest_path` NULL where the target is not yet determined. State that the 'existing record' wording applies to routes A and B only.

### [MINOR] A suffixed move is named `renamed` in F16 and `moved` in route A
**Where:** F16 (line 131: `renamed`); route A step 4 (line 224: 'bijwerken naar `moved`'); AC3a route A collision (line 266: `moved` under a next free name).
**Claim:** A suffix rename gives `renamed`. Route A always ends in `moved`.
**Reality:** The two are mutually exclusive for a same-volume move that hits a name collision. Route B step 7 says 'eindresultaat' without settling it.
**Consequence:** The test (line 266) passes with either choice. The summary per result kind (F18) differs depending on which one is picked.
**Fix:** Decide one rule. For example, `renamed` wins whenever a suffix was used, in copy and move alike. Align F16, route A step 4 and the AC3a test with it.

### [MINOR] Route C has no in-process failure tests
**Where:** AC3a (lines 258–261, 267–269); route C steps 3–5.
**Claim:** The failure cases (half copy, publish error, size mismatch) assert 'no file under the final name' and 'the temp file is cleaned up'.
**Reality:** Those assertions are phrased for route B. In route C the own file sits under the final name by design. Route C has tests only for the collision and the two crash cases. A copy error, a size mismatch and a metadata failure are not covered for route C. A test that runs route B with the capability injected away would assert something else.
**Consequence:** A route C cleanup bug on a normal error would go untested. Examples: the half file under the final name is left behind, or the 'delete own file' step is skipped. The size-mismatch case is the exact place where own-file deletion matters.
**Fix:** Parametrise the cases at lines 258, 261 and 272 over route B and route C. For route C, assert that the own file at the final name is removed and no foreign file is touched.

### [MINOR] The capability probe is only half specified for macOS
**Where:** F15 (line 123); NF4 (line 213).
**Claim:** `getattrlist` with `VOL_CAP_INT_RENAME_EXCL` determines the route once per run.
**Reality:** The spec does not say to check the bit in `vol_capabilities.valid[]` before reading `capabilities[]`. A volume that does not report the bit can read as 'unsupported', which falls safely to route C. A volume (typically SMB) that reports support but returns ENOTSUP or EINVAL on the actual `renamex_np` call is handled only through the generic 'other error → failed' case (line 259). Every file in that run would then fail.
**Consequence:** Safe against overwrites, but the run can fail on a quirky share instead of degrading. The AC7 dmg tests would not reveal this.
**Fix:** State that the valid bit must be checked. Optionally say that ENOTSUP or EINVAL on the first publish switches the run to route C, since no file has been published at that point. Alternatively, accept the failure explicitly.

### [MINOR] The retry counter wording is ambiguous
**Where:** NF4 'Algemeen' (line 217); AC3a (line 265).
**Claim:** 'maximaal 3' collisions per file, after which the result is `failed`.
**Reality:** It is unclear whether this means 3 attempts in total or 3 retries after the first attempt. The AC says 'drie keer EEXIST → failed', which implies that the third EEXIST is fatal.
**Consequence:** Off-by-one behaviour between implementation and test is possible. The test can still pass either way if the hook is scripted per attempt.
**Fix:** Write 'at most 3 attempts; the third EEXIST gives `failed`'.
