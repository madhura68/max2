## Findings

### [MAJOR] Route C crash cleanup proves ownership by path only and can delete a foreign file
**Where:** NF4 'Algemeen' (line 216) and 'Opruimen / Na een crash' (line 250); route C step 3 (line 238); AC3a lines 268 and 273; F19b step 2 and F19c.
**Claim:** At the next start cleanup removes 'alleen de bestanden waarvan het pad nog als `temp_path` in hun `pending`-records staat, en alleen als ze nog bestaan'. 'Andere bestanden worden nooit door de opruiming verwijderd.' NF4 says a transfer never deletes a file that is not the app's.
**Reality:** In route B the path is `.macsearch-<UUID>.tmp`. A unique, hidden name makes 'the path exists' a reasonable proof of ownership. In route C `temp_path == dest_path`, a natural name such as `<dest>/<keyword>/<date>/IMG_001.jpg`. Between the crash and the next start (hours or days) the following can happen:
- The user sees a half or empty file in the destination folder, deletes it in Finder, and copies the correct file in by hand under the same name.
- A different tool or sync client creates a file under that name.

At the next start the `pending` record still names that path and the file 'still exists', so cleanup deletes the foreign file.

The same happens without a crash. Route C 'Bij een fout' deletes the own file, but if the following record update fails (F19b), the `pending` record keeps its `temp_path`. If the `aborted` write also fails, the run is later set to `interrupted` and cleanup runs against a path that is now free for reuse.

The tests would not show this. AC3a line 273 uses a foreign file with a different name (`.macsearch-other.tmp`). Line 268 uses a foreign file 'in dezelfde map' that also has a different name.
**Consequence:** NF4's absolute invariant is broken in a realistic, if rare, sequence. JP's decision accepts removing a half-written *app-owned* file. It does not accept removing a foreign one, and the task says the mechanism must never delete one. Building this as written yields a latent data-loss defect that no listed test detects.
**Fix:** Make ownership more than a path match:
- At route C step 3, record a file identity in the `pending` record (device and inode via `fstat` on the O_EXCL fd, or `fileResourceIdentifier`, plus optionally the creation date).
- Have cleanup delete only if the identity at the path still matches. If the identity cannot be determined (exFAT or SMB without stable inodes), fall back to a conservative rule: leave the file and keep the record.
- On any error path that deletes the own file, set `temp_path = NULL` best-effort.
- Add an AC3a case: a `pending` route C record whose path now holds a foreign file with different content → the file is byte-identical after the start.

### [MINOR] Route C retry: there is no 'existing record' at the step 2 EEXIST
**Where:** line 237 (route C step 2) vs lines 238 and 245–246 and F19b (line 143).
**Claim:** A retry always updates the existing record. In route C the first EEXIST occurs before the record exists.
**Reality:** The record is inserted at step 3 only. F19b covers the identical case ('insert directly if there is no record'). The 'Anders' branch and the three-times-EEXIST failure for route C do not say that the first record is inserted lazily or that `failed` needs an insert.
**Consequence:** Ambiguity, likely resolved differently by an implementer. 'Precies één record' for route C is hard to test.
**Fix:** Add one sentence: a record is inserted on the first outcome that needs one (`pending` at step 3, or the final result for identical or failed), and later attempts update it.

### [MINOR] Unspecified: failure of the route C step 5 update (`temp_path = NULL`)
**Where:** line 240 and F19b step 2.
**Reality:** If the update fails, the file is complete, the source is still there, and the `pending` record still has `temp_path`. The spec does not say that the source is then NOT deleted. F19b's wording 'dit bestand is al verwerkt' suggests the opposite. If an implementer deletes the source anyway and the later cleanup deletes the complete file, the data is gone.
**Fix:** State that on a failure of step 5 the source is never deleted and the batch stops. Optionally add an AC3a case 'step 5 update fails → source still exists'.

### [MINOR] `moved` vs `renamed` when a move collides
**Where:** F16 (line 131), route A step 4 (line 224), AC3a line 266 vs line 263.
**Reality:** F16 and AC3a line 263 give `renamed` for a collision with different content. AC3a line 266 (route A) expects `moved` under a following free name, and route A step 4 always writes `moved`. The result list in F17 has no combined value.
**Fix:** Pick one rule, for example that `renamed` also applies to moves, and align route A step 4 and line 266.

### [MINOR] Route C identical-content retry and `EEXIST` on a real SMB share are untested
**Where:** AC3a lines 264 and 267.
**Reality:** The identical-content retry is only tested for route B (a temp file to delete). In route C there is no own file at that point, and the path that inserts the record and sets `skipped_identical` is untested. `O_EXCL` on SMB is not tested, and AC7 covers only an exFAT dmg.
**Fix:** Run the identical-collision case once with the capability disabled. Note that `O_EXCL` on SMB is accepted as unverified.

### [MINOR] AppleDouble (`._*`) sidecar files on exFAT and SMB are not considered
**Where:** F15, route B/C step 4 (`fcopyfile … COPYFILE_ALL`), AC7 line 299.
**Reality:** On volumes without native xattr support, copying xattrs creates `._<name>` sidecar files. In route C, cleanup after a crash deletes only `temp_path`. AC7 checks only for `.macsearch-*.tmp`, so sidecar leftovers are not seen.
**Fix:** Either state explicitly that the `._` sidecar belongs to the own file and is removed with it, or restrict the copy on route C to data plus stat and leave out the xattrs. Add a `._*` check to AC7.

## macOS feasibility
`VOL_CAP_INT_RENAME_EXCL` via `getattrlist` with `ATTR_VOL_CAPABILITIES` exists. `renamex_np(…, RENAME_EXCL)` is correct for a same-volume move. `O_EXCL` on the final name is feasible. Setting the creation date needs `setattrlist` with `ATTR_CMN_CRTIME`, and the modification date `futimens`. The spec does not name these calls, but that is not a defect.
