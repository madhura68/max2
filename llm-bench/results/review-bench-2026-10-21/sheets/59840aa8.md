## Rapport

### [MAJOR] Route C does not preserve ownership if its final path is replaced
**Where:** `doc`: lines 216–218, 235–242, 248–250. **Claim:** NF4 says transfers must not overwrite or delete a file that is not the app’s; route C exclusively creates the final path, records that path as `temp_path`, and later clears `temp_path` before deleting the move source. **Reality:** Ownership is represented only by a pathname. If another process removes or replaces that path after MacSearch creates/opens it, MacSearch can continue writing through its open descriptor to the original file while the path now names a foreign file. Route C can then clear `temp_path` and delete the source, leaving the foreign replacement at the destination. If an error or crash cleanup instead unlinks `temp_path`, it can delete the replacement. The spec does not require verifying that the path still identifies the exclusively created file before cleanup, declaring the file complete, or deleting the source. **Consequence:** A foreign file can be deleted, or a move can delete its source without leaving the transferred content at the destination—contrary to NF4/F15 and the binding protection requirement. **Fix:** Track and verify the created file’s identity (including before unlink/cleanup, clearing `temp_path`, and source deletion); define a safe failure path if the final path no longer identifies that file. Add injected replacement tests for route C and cleanup.
