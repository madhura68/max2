## Findings

### [MINOR] Cleanup precision in Route C: file between step 4 and step 5

**Where:** `sources/doc` NF4 Route C steps 4–5 (lines 239–240), joined with NF4 "Opruimen / Na een crash" (line 250), against AC3a "Route C, crash na `temp_path = NULL`" (line 269).

**Claim:** NF4 step 5 says "Het record bijwerken met `temp_path = NULL`: het bestand is nu compleet en wordt niet meer opgeruimd." NF4 "Na een crash" says cleanup removes "alleen de bestanden waarvan het pad nog als `temp_path` in hun `pending`-records staat". The implicit contract: cleanup removes incomplete files, complete files survive.

**Reality:** In Route C, `dest_path = temp_path` (per step 3, line 238). A crash between step 4 finishing (file complete, dates set, contents written) and step 5 committing (UPDATE temp_path = NULL) leaves the pending record with `temp_path = dest_path` set and the file at that path complete. On the next app launch, F19c marks the run `interrupted` and the cleanup rule, taken literally, unlinks the complete file. AC3a only covers crashes "na `temp_path = NULL`" — the symmetric crash window between copy-complete and temp_path-NULL is not exercised.

**Consequence:** In this narrow window, an app-owned complete file under the destination name is removed by cleanup. NF4's strong "no overwrite or delete of foreign files" still holds (the file is app-owned), so the safety story is intact. The cost is user-visible: a successful copy silently disappears, the record remains `pending` in SQLite, the user has to redo the operation. Route A and Route B do not have this corner because Route B's temp_path points at the pre-rename path (which no longer exists if the rename committed) and Route A has no temp file. Only Route C's symmetric `temp_path = dest_path` exposes it.

**Fix:** MINOR — clarify the contract. Either (a) tighten the cleanup rule so the next-startup unlink happens only when the record's `result = 'pending'` AND a sentinel flag (e.g. `copy_complete = 0` set on insert, cleared on step-5 commit) says the copy is not complete; (b) wrap the step-4 finish (fsync + close) and the step-5 UPDATE in a single transaction or batched with an explicit barrier so the half-state cannot land; or (c) explicitly carve out in NF4 that "in the route C window between copy and temp_path=NULL the file may also be removed at the next start", and add an AC3a case asserting that complete-file-removed behaviour. (a) is the smallest remedy that preserves the existing intent.
