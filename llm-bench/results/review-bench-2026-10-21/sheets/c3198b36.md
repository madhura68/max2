## Findings

### [MINOR] Route C crash window between full copy and `temp_path = NULL` deletes a COMPLETE file at next start
**Where:** doc:239-240 (Route C stap 4-5), doc:250 (Opruimen), doc:213/251 (accepted trade-off); test gap at doc:268-269.
**Claim:** On volumes without `RENAME_EXCL`, 'na een crash tijdelijk een **half** bestand van de app onder de definitieve naam staan. Dat wordt bij de volgende start opgeruimd' (doc:213). Cleanup deletes files whose path is still `temp_path` in a pending record (doc:250).
**Reality:** In Route C, `temp_path` is set to the final destination name (doc:238) and cleared only in stap 5 (doc:240). A crash after the copy in stap 4 has fully completed but before the stap 5 write leaves a **complete** destination file with `temp_path` still set and the record still `pending`; startup cleanup deletes it. Cleanup cannot distinguish complete from half-written — it deletes by `temp_path` presence alone. The existing case (doc:269) covers the opposite window (crash after `temp_path = NULL`, before source delete), not this one.
**Consequence:** A fully written destination file is removed at the next start. Self-healing, not data loss: the source is deleted only after `temp_path = NULL` (doc:240), so it is still present and a re-run reproduces the destination. A strict superset of the accepted half-file trade-off.
**Fix:** defer/clarify — state in NF4 Opruimen that a Route C file fully written but not yet promoted may also be removed at startup (source intact), and add an AC3a case: route C, crash after the stap-4 copy completed, before stap 5 → at startup the destination is gone, the source is intact, and a re-run recovers it.

### [MINOR] Retry rule updates only `dest_path`; a Route C retry must also update `temp_path`
**Where:** doc:246 ('`dest_path` in het bestaande record wordt bijgewerkt en de app gaat verder bij … route C stap 2'), doc:237-238.
**Claim:** On retry the existing record is updated, then Route C restarts at stap 2, where a new file is created exclusively under the new name.
**Reality:** For Route C, `temp_path` equals the app's file (doc:238). On retry, the old `temp_path` (equal to the old dest, where no file was ever created — O_EXCL failed) remains in the record unless the implementation also rewrites it to the newly created file. Read literally, the retry update covers `dest_path` only.
**Consequence:** If implemented literally, a crash during the copy of the retry's new file leaves a half file whose path is in no `temp_path` — residue of the acknowledged class (doc:251) but with an avoidable cause, and it defeats the doc:250 guarantee for that file.
**Fix:** one clause — extend the retry rule (doc:246) to say the record update also sets `temp_path` to the file (re)created in route C stap 2.

### [MINOR] 'maximaal 3' counter wording and AC3a 'Drie keer EEXIST' need a shared reading
**Where:** doc:217 ('één pogingenteller … maximaal 3. Daarna is het resultaat failed'), doc:265.
**Claim:** One counter for all 'exists' collisions, capped at 3, after which the result is `failed`.
**Reality:** The AC3a case passes under the reading 'on the third EEXIST the result is failed', so there is no contradiction with AC3a. But the sentence does not say whether the counter counts attempts or collisions, nor the ordering of 'check counter' vs 'do F16 again' (doc:244) at the third EEXIST, which an implementer could resolve differently.
**Consequence:** Clarity only; two reasonable implementations behave identically on every tested case.
**Fix:** one-line clarification that the counter counts EEXIST collisions and fails on the third, before running F16 again.

### [MINOR] Post-publication / pre-source-delete crash window untested
**Where:** doc:231-232 (Route B stap 5-6), doc:240 (Route C stap 5); no AC3a case covers a crash between publication success and source deletion.
**Claim:** AC3a covers source-delete failure via injection (doc:260) and the route C window after `temp_path = NULL` (doc:269).
**Reality:** A crash in the gap (publication succeeded, source delete not yet executed) is not covered. Consequence is benign and follows from existing rules: cleanup finds `temp_path` no longer existing (route B) or the record already at `temp_path = NULL` (route C), so nothing is deleted; a re-run hits F16, sees identical content at the destination, and returns `skipped_identical` with the source left in place — the §1a behavior for identical files. Not a defect; an unstated, untested window.
**Fix:** defer, or add one AC3a case pinning the benign re-run semantics (complete destination survives startup; source still present; re-run yields `skipped_identical`).
