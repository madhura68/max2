## Findings

### [MINOR] Restart cleanup deletes by path only, without re-verifying ownership
**Where:** `doc`:250 (NF4, Opruimen) and `doc`:238 (route C stap 3).
**Claim:** Cleanup deletes "only the files whose path still stands as `temp_path` in their `pending`-records, and only if they still exist".
**Reality:** In route C, `temp_path` equals the final destination name (e.g. `IMG_1234.jpg`). The check is existence-by-path; nothing verifies that the file now at that path is still the one the app created (e.g. by comparing a recorded `fileResourceIdentifier`, inode, or creation date captured at `O_EXCL` time). A file placed at that exact name between the crash and the next start — a manual restore, a sync client, a Time Machine recovery — is deleted as if it were the app's half-written file.
**Consequence:** In a narrow window the mechanism the round is asked to check ("never delete a foreign file") can be violated, though only after external interference on a path the app briefly owned.
**Fix:** Record the created file's identity (e.g. `fileResourceIdentifierKey` or size+birth time) in the pending record and verify it before `unlink` in the startup cleanup. Deferable to a SCHRAP if the single-user risk is judged acceptable; the spec should at least state the assumption.

### [MINOR] Route B's label under-describes its own scope
**Where:** `doc`:226.
**Claim:** "Route B: kopiëren of verplaatsen **tussen volumes**, doelvolume mét `RENAME_EXCL`."
**Reality:** A copy within the same volume (source volume = destination volume) with capability present is neither route A (moves only) nor route C (no capability); it must go through route B, which works fine for it. The dispatch's own description ("copy, or cross-volume move") is broader than the document's header.
**Consequence:** An implementer reading only the headers could conclude same-volume copies are unspecified.
**Fix:** Reword the header to "kopiëren (elk), of verplaatsen tussen volumes, doelvolume mét `RENAME_EXCL`".

### [MINOR] AC3a's "real FileOps" sentence conflicts with the cases that need injection
**Where:** `doc`:257 vs `doc`:258–265.
**Claim:** "De gevallen voor collision, publicatie, route C en metadata draaien op de **echte** `FileOps`", while the same AC3a requires "foutinjectie op elke stap" and "via een hook in `FileOps`".
**Reality:** Several of the named cases (copy breaks halfway, publish fails with non-`EEXIST`, three `EEXIST`s, the between-F16-and-publication hook) cannot run on an unmodified real `FileOps`.
**Consequence:** Ambiguity about which cases run real I/O with injected faults versus fully mocked operations; two implementers can build different test setups and both claim AC3a.
**Fix:** State that all cases perform real file I/O through a `FileOps` wrapper whose fault points are injectable, so "real operations, injected failures" is the single reading.

### [MINOR] Attempt-counter scope is ambiguous against F16's own candidate walk
**Where:** `doc`:217 vs `doc`:131 and `doc`:228.
**Claim:** "Per bestand is er één pogingenteller voor alle botsingen op 'bestaat al': maximaal 3."
**Reality:** It is unclear whether (a) F16's own suffix scan — where `(2)` and `(3)` already exist with different content before the first free name — counts as collisions, and (b) whether a collision on the `.macsearch-<UUID>.tmp` temp name (doc:228) counts toward the same 3.
**Consequence:** Implementations may legitimately differ on when the counter trips; the "three times `EEXIST`" test (doc:265) only pins the publication side.
**Fix:** One sentence: the counter counts only `EEXIST` at the exclusive step of the chosen route; F16's pre-scan and temp-name UUID retries do not consume attempts.

### [MINOR] Route B move: crash window between publish and source deletion has no AC3a case
**Where:** `doc`:230–232 (route B stappen 5–6) vs `doc`:269.
**Claim:** AC3a covers "crash na `temp_path = NULL` maar vóór het verwijderen van de bron" for route C only.
**Reality:** The analogous route B window (crash after `renamex_np` publish, before the source delete or the record update) is untested. The outcome is benign by construction — the temp path no longer exists, so cleanup deletes nothing; the complete destination and the intact source both remain — but that benign outcome is asserted nowhere.
**Consequence:** A regression that reorders route B steps 5–6 (deleting the source before publishing) would not be caught by any listed case.
**Fix:** Add the mirrored route B case to AC3a; alternatively fold it into the existing case as "(route B and C)".

### [MINOR] F19b's "geen transfer" phrasing is wrong on the retry-identical path
**Where:** `doc`:143 vs `doc`:245.
**Claim:** "Bij `skipped_identical` vindt er geen transfer plaats."
**Reality:** On the retry path, data has already been copied (to the route B temp file, or the route C final-name file opened before the `EEXIST`) before the collision is resolved as identical; the own file is then deleted (doc:245).
**Consequence:** Purely cosmetic; no code decision hinges on it, but a literal reading conflicts with the retry section.
**Fix:** Reword to "bij een verse vaststelling vindt er geen transfer plaats; op een herpoging wordt het eigen bestand verwijderd".

### [MINOR] Fallback when the capability query itself fails is unspecified
**Where:** `doc`:123 (F15) and NF4 route selection.
**Claim:** The route is chosen once per run from `getattrlist`/`VOL_CAP_INT_RENAME_EXCL`.
**Reality:** The document does not say what happens if `getattrlist` on the destination volume fails (unmounted mid-run, I/O error). Both defaults are data-safe — assuming capability present yields `renamex_np` errors on publish (non-`EEXIST` → `failed`, own file removed); assuming absent selects route C — but the spec should not leave the choice to the implementer.
**Consequence:** Divergent implementations; one run-wide error versus a per-file `failed`, with no data risk either way.
**Fix:** One sentence in F15: on query failure, treat the volume as lacking `RENAME_EXCL` (route C) and continue.

## Necessity
"None" is my answer for removal: the attempt counter, the retry-updates-existing-record rule, and the `temp_path = NULL` ordering are all load-bearing for the no-foreign-overwrite guarantee; the UUID-collision test (doc:262) is cheap and directly exercises the invariant. The `link` tier and plain-rename fallback are correctly gone.
