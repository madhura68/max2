## Findings

### [BLOCKER] Crash cleanup can delete a foreign replacement at an app-owned pathname

**Where:** `doc`, `sources/doc:201`, `sources/doc:216`, `sources/doc:248–251`; cleanup acceptance cases at `sources/doc:268–273`.

**Claim:** NF4 promises never to delete a file that is not the app's. Startup cleanup deletes an existing file if its pathname remains in a pending action's `temp_path`.

**Reality:** The database stores only a pathname, not a persistent identity for the exclusively created file. Consider route C: the app creates and records the final-name file, writes half of it, and crashes. Before restart, the user removes that partial file and puts an unrelated complete file at the same pathname. The prescribed startup cleanup deletes that unrelated file. Route B has the same problem if its recorded temporary pathname is reused after a crash. Exclusive creation established ownership of the original object, not permanent ownership of its name. AC3a preserves a foreign file elsewhere in the directory, so it can pass despite this defect.

**Consequence:** Following the specified cleanup algorithm produces foreign-file deletion, violating the explicit protection boundary. This is distinct from the accepted half-written route-C destination.

**Fix:** Repair ownership tracking and cleanup: persist the created file's identity and require cleanup to establish that it is deleting that same object, not merely the current occupant of its name. Specify protection against substitution between verification and deletion; when ownership cannot safely be established, leave the file and report it rather than delete it. Add restart tests replacing the recorded route-B and route-C pathname with a foreign file, asserting that the replacement remains byte-for-byte unchanged. A pathname check, or an unprotected identity-check-then-unlink sequence, is insufficient for the unconditional guarantee.

### [MAJOR] Route C's first EEXIST retry requires a nonexistent record

**Where:** `doc`, `sources/doc:143`, `sources/doc:218`, `sources/doc:235–246`; route-C collision test at `sources/doc:267`.

**Claim:** Every retry updates the existing record and never inserts a second record. Route C sends an `EEXIST` from its exclusive-create step to that shared retry procedure.

**Reality:** Route C inserts its first pending record only at step 3, after successful exclusive creation. If a foreign file appears between F16 and step 2, `open(...O_EXCL...)` returns `EEXIST` before there is any record. For different content, the shared retry procedure nevertheless requires updating `dest_path` in the existing record before returning to route C step 2. That update has no target. F19b handles an absent record for an identical-content skip, but supplies no corresponding rule for this different-content retry. The route-C test only asserts preservation of the foreign file and absence of an inappropriate rename; an implementation that simply fails this transfer could satisfy those assertions.

**Consequence:** The newly introduced route cannot follow the retry procedure as written. Implementers must invent record-creation semantics, potentially mishandling logging or failing an otherwise valid collision-and-suffix transfer.

**Fix:** Repair the retry rule to distinguish pre-record collisions from retries with an existing record. For route C, perform F16 and retry exclusive creation without a database update until acquisition succeeds; then insert exactly one pending record before writing bytes. Preserve the single attempt counter. Expand the route-C collision test to require successful transfer under the next free name, the expected result, exactly one action record, and no remaining pending record.

### [MINOR] Route A's suffixed result conflicts with F16

**Where:** `doc`, `sources/doc:131–132`, `sources/doc:220–224`, `sources/doc:266`.

**Claim:** F16 labels a different-content conflict resolved with a Finder-style suffix as `renamed`. Route A always updates the record to `moved`, and its collision acceptance case explicitly expects `moved` under a subsequent free name.

**Reality:** A same-volume move with a suffix has two different prescribed final results. This is a reporting-contract contradiction rather than a file-publication failure.

**Consequence:** Implementers and tests can disagree about action-log and summary counts even when the transfer itself is correct.

**Fix:** Clarify the intended precedence. If F16's `renamed` result applies across all routes, change route A's final-result instruction and collision expectation accordingly. Otherwise state the route-A exception explicitly.
