## Samenvatting

Round 5, revision 5 (sha256 7d5e3587…fadaf, read in full). Findings: 0 BLOCKER, 0 MAJOR, 7 MINOR. Verdict: GO.

Most important finding: the crash-cleanup and ordering invariants are path-based and assume nothing is lost after a power loss. In route C, `temp_path = NULL` is written before the source is deleted. If that write or the destination data is not durable, a move can end with the source gone and the cleanup deleting a complete file. This needs power loss, not an app crash, so it is MINOR. A related MINOR: the cleanup deletes by path without checking the file's identity, and it is never retried when the volume is absent at start.

Route C ordering is sound for app crashes:
- The source is deleted only after `temp_path = NULL`.
- A crash before that point leaves the source intact, so the cleanup can only delete an incomplete copy.
- A crash after it leaves both files.

Scope: nothing needs to be cut for acceptance. Route A is an optimisation (a same-volume move via B or C would also work), but it keeps large moves cheap and atomic and has its own tests. I would not remove it. Dropping the `link` tier and the plain-rename fallback was correct.

Per fix:
1. No overwrite fallback: HELD. There is no plain `rename` anywhere. Every publication is `renamex_np(RENAME_EXCL)` or `O_EXCL` on the final name. See MINOR 4 for a validity-bit detail.
2. Retry bookkeeping: PARTIALLY HELD. Routes A and B are consistent. Route C has no existing record at an `EEXIST` retry, which contradicts the wording "always update the existing record" and "exactly one record" (MINOR 1). The result for a suffixed name is also inconsistent between route A and B (MINOR 2).
3. Metadata: HELD (explicit dates, warning on failure, AC3a has both cases).
4. Folder creation after the `search_run` insert: HELD (F14, AC4).
5. Tests: PARTIALLY HELD. The route C crash tests do not say how a crash is simulated, so they could pass through the normal error-cleanup path (MINOR 5). Route C has no identical-collision test (MINOR 6).

## Crash-window analysis (all routes)
- **Route A:** a crash after the rename and before the record update leaves a `pending` record without `temp_path`. Nothing is deleted and the file is complete. Safe.
- **Route B:** a crash after publication and before the record update leaves a `temp_path` that no longer exists. The cleanup skips it because of "alleen als ze nog bestaan". Safe.
- **Route C:**
  - A crash during the copy deletes only the half file, and the source is intact.
  - A crash between the end of the copy and `temp_path = NULL` deletes a complete copy, but the source is still there. Data-safe.
  - A crash after `temp_path = NULL` and before the source deletion leaves both files.
  - Safe against app crashes.

## Findings

### [MINOR] Route C has no "existing record" at an EEXIST retry
**Where:** NF4 "Algemeen" (line 218), route C step 2 (line 237), "Herpoging na EEXIST" (lines 243–246), F19b step 1 (line 143), AC3a "Drie keer EEXIST" (line 265).
**Claim:** a retry always updates the existing record, there is never a second record, and "precies één record" holds.
**Reality:** in route C the `pending` record is inserted only at step 3, after the successful `O_EXCL`. An `EEXIST` at step 2 therefore happens before any record exists. The `skipped_identical` and `failed` outcomes after a route C retry have no record to update. The spec only says what to do for `skipped_identical` in F19b. For `failed` it is silent, and the schema allows `dest_path` to be NULL for a failed record.
**Consequence:** an implementer must guess when the record is created in route C. The test "exactly one record" is only meaningful for routes A and B.
**Fix:** add one sentence: "If no record exists yet (route C step 2), the retry result is inserted as a new record once, with its final result." Also name route C explicitly in the identical/failed collision tests.

### [MINOR] Result for a suffixed name differs between route A and B/C
**Where:** route A step 4 (line 224), AC3a line 266 ("`moved` onder een volgende vrije naam"), F16 line 131 (`renamed`), AC3a line 263.
**Claim:** a suffixed name gives `renamed` (F16, AC3a line 263), but route A gives `moved` under a suffixed name.
**Reality:** two tests and two spec places prescribe different result values for the same situation. It is also unspecified whether `renamed` covers a move.
**Consequence:** a test or the code will fail on the first implementation. Reporting and history may be inconsistent.
**Fix:** choose one rule. For example: `renamed` for any suffixed name, in copy and in move mode, and `moved` only for the original name. Then change route A step 4 and the AC3a line 266 case accordingly.

### [MINOR] The cleanup is path-based only and is not retried
**Where:** NF4 "Opruimen, Na een crash" (line 250), AC3a line 273.
**Claim:** after a crash, only files whose path is `temp_path` in a `pending` record are deleted, and only if they exist. Other files are never removed by the cleanup.
**Reality:**
- (a) Nothing checks that the file is still the app's own. Between the crash and the restart, a foreign file with the same name could take its place. In route C the name is the final, visible name.
- (b) The cleanup only covers runs that become `interrupted` at this start. If the destination volume is not mounted then (typical for an external exFAT disk), the half file stays under its final name for good. The next run treats it as a foreign colliding file, so it is not deleted, which is safe. But it contradicts "wordt bij de volgende start opgeruimd".
**Consequence:** a very small window in which a foreign file could be deleted (the headline of NF4). Half files left behind on unmounted volumes.
**Fix:** store identity at creation (for example `fileResourceIdentifier` plus size or inode) in the record and verify it before deleting. For (b), also retry unresolved `temp_path` records of earlier `interrupted` runs at each start. Alternatively, document this explicitly as an accepted risk.

### [MINOR] Durability ordering before source deletion is not specified
**Where:** F15 (line 125), NF4 route B step 6, route C step 5.
**Claim:** the source is deleted only after a successful and checked move.
**Reality:**
- No `fsync` (or `F_FULLFSYNC`) is required on the destination data before the source is deleted.
- In route C, no durable commit of `temp_path = NULL` is required before the source is deleted.
- SQLite on macOS does not use full fsync by default.
- After a power loss (not an app crash), a move can lose both the destination data and the source. In route C, the cleanup could also delete a complete file whose `temp_path = NULL` update was rolled back.
**Consequence:** a data-loss window under power loss only. App crashes are safe.
**Fix:** one line: `fcntl(F_FULLFSYNC)` on the destination fd before deleting the source in moves. Also use a synchronous, full-fsync GRDB write for the `temp_path = NULL` update, or accept the risk explicitly.

### [MINOR] A crash is not defined in the tests; the update of `temp_path = NULL` has no failure handling
**Where:** AC3a lines 268–269 and F19b step 2 (line 146), route C step 5 (line 240).
**Claim:** tests for "crash after a half copy" and "crash after `temp_path = NULL`".
**Reality:**
- (a) The `FileOps` error injection normally runs the normal error path, which already deletes the own file. The tests could therefore pass without the startup cleanup running at all. The spec does not require the crash to be simulated as an abort without in-process cleanup (a throw that bypasses the cleanup, or a fresh store instance on the same database).
- (b) A failing `temp_path = NULL` update (route C step 5) is not specified. F19b step 2 says "already processed" for the final-result update, but here the move has not yet deleted its source. No test covers this case.
**Consequence:** a test can pass while its named defect is present.
**Fix:** (a) define the crash simulation: halt the `FileOps` call chain without cleanup, then start a new `HistoryStore` and run the startup cleanup. (b) Specify: if the update fails, delete the own file, keep the source and report `failed`; add one test.

### [MINOR] Route C lacks an identical-content collision test and a result assertion
**Where:** AC3a line 267.
**Claim:** the route C collision test only asserts that the foreign file is unchanged and that no `rename` is called.
**Reality:** there is no assertion on the result (`renamed` under a free name) or on the record. There is also no case with identical content (`skipped_identical`, source left in move mode) in route C. The identical-content retry in route C is exactly the round-4 MAJOR 2 scenario.
**Consequence:** the stale-record defect could return in route C without a test failing.
**Fix:** add "route C, collision with identical content: `skipped_identical`, exactly one record, no `pending`, source intact", and add the result assertion to the existing case.

### [MINOR] Details of the capability check and of `fcopyfile` on non-native filesystems
**Where:** F15 line 123, route B/C step 4.
**Claim:** `getattrlist` with `VOL_CAP_INT_RENAME_EXCL` decides the route. `fcopyfile(…, COPYFILE_ALL)` writes to the opened descriptor.
**Reality:**
- (a) The capability is only meaningful if the matching bit in the `valid` mask of `vol_capabilities_attr_t` is set. The spec does not say that an unset valid bit must count as "no capability" (route C).
- (b) On filesystems without native xattr support (exFAT), copying xattrs may create `._name` AppleDouble sidecar files. The `fcopyfile` descriptor route may fail or behave differently there. The cleanup would not remove such a sidecar.
**Consequence:** a wrong route on some volumes, or leftover sidecar files. AC7 covers exFAT manually.
**Fix:** state that an unset valid bit counts as "no capability". Add to AC7 a check that no stray `._*` or `.macsearch-*` files remain and that a failing xattr copy is only a warning.

## Verdict
GO: zero BLOCKER and zero MAJOR. All findings can be fixed in the spec text or tests without a design change. The narrowing trend is genuine: the NF4 routes now never overwrite a foreign file, and every crash window I traced in routes A, B and C is safe against an app crash.
