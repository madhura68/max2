# Transcript c9e731 (R06: review zonder bestand)

### Gebruiker

Kun je mijn docker-compose op security laten reviewen?

### Model

Om een sterke prompt voor de security review te schrijven, heb ik wat meer details nodig:

1. Om wat voor soort applicatie gaat het (bijv. een publieke webapp, een intern dashboard of een lokale dev-omgeving)? [standaard: een webapplicatie die publiek toegankelijk is]
2. Wil je dat Opus alleen de `docker-compose.yml` beoordeelt, of ook de bijbehorende `Dockerfiles` en netwerkconfiguraties? [standaard: zowel de compose-file als de Dockerfiles]
3. Moet de review zich richten op specifieke standaarden (bijv. CIS benchmarks) of algemene best-practices? [standaard: algemene security best-practices voor Docker en containers]
4. Hoe ga je de bestanden aanleveren? [standaard: ik plak de code in de chat of upload de bestanden als bijlage]

Zodra ik dit weet, maak ik de definitieve prompt voor je.

### Gebruiker

Akkoord met je voorstellen. Het is een compose-bestand voor een paar containers op mijn thuisserver.

### Model

Hier is de complete prompt voor de security review.

```markdown
<context>
Ik beheer een thuisserver waarop een aantal containers draaien via Docker Compose. Omdat deze server mogelijk vanuit het internet bereikbaar is of gevoelige data bevat, wil ik zeker weten dat de configuratie veilig is en dat ik geen onnodige risico's loop.
</context>

<material>
Zie de bijgevoegde of hieronder geplakte docker-compose.yml en de bijbehorende Dockerfiles.
</material>

<task>
Voer een security review uit op de verstrekte Docker-configuraties. Identificeer kwetsbaarheden, onveilige configuraties en wijk af van best-practices voor container-security.
</task>

<constraints>
- Beoordeel zowel de docker-compose.yml als de Dockerfiles.
- Focus op algemene security best-practices (denk aan: root-privileges, netwerkisolatie, resource limits, secrets management en image-versies).
- Rapporteer elk gevonden issue met een bijbehorend ernstniveau (bijv. Laag, Medium, Hoog, Kritiek).
- Geef bij elk issue een concrete suggestie voor verbetering of een gecorrigeerd codefragment.
- Indien informatie ontbreekt om een oordeel te vellen, geef dit dan aan in plaats van aannames te doen.
</constraints>

<done_when>
Alle bestanden zijn geanalyseerd en elk geïdentificeerd security-risico is voorzien van een ernstniveau en een concreet oplossingsvoorstel.
</done_when>

<output_format>
Structureer de review per container of per thema (bijv. 'Netwerk', 'Rechten', 'Images'). Gebruik een heldere lijst of tabel voor de bevindingen. Sluit af met een korte samenvatting van de algemene security-status van de setup.
</output_format>
```

**Aannames:**
- De server wordt gebruikt voor eigen gebruik (thuisserver), maar security is prioriteit.
- Je levert zowel de compose-file als de Dockerfiles aan.
- De review richt zich op algemene best-practices in plaats van specifieke compliance-standaarden.

**Instellingen:**
- Effort: medium.
- Bijlage: Voeg je `docker-compose.yml` en alle relevante `Dockerfile`s toe aan het gesprek.
