# Transcript d42464 (D04: feit niet in de docs)

### Gebruiker

Laat de harness bij een mislukte job een melding naar ons Slack-kanaal sturen.

### Model



Vier vragen om de prompt scherp te krijgen:

1. Welke mislukkingen moeten een melding geven? [standaard: elke job die als `failed` wordt afgesloten (ook "worker gestopt"), plus `budget_exceeded` en `timed_out`; een worker-crash met systemd-herstart ook]
2. Via welk Slack-mechanisme? [standaard: een incoming webhook, URL uit een omgevingsvariabele (bijv. `SLACK_WEBHOOK_URL`), in lijn met de conventie "secrets horen in de omgeving, niet in de config" (manual/readme)]
3. Wat moet de melding bevatten? [standaard: job-id, jobsoort (IDEA_CHAT/TASK_IMPLEMENTATION), eindstatus, faalreden en de run-dir]
4. Werk ik met Claude Code in de agent-harness-repo, en moet de documentatie (manual/readme, betrokken runbook) ook mee worden bijgewerkt? [standaard: ja, en het geheel moet `npm run verify` (lint + typecheck + test, zonder netwerk) groen laten]

Extra aannames die ik al maak: een mislukte Slack-post mag de worker nooit breken (best-effort met timeout) — dat schrijf ik in de prompt als eis.

### Gebruiker

Akkoord met je voorstellen.

### Model



```
<context>
Ik werk met Claude Code in de repo ~/Development/agent-harness: een standalone agent-harness v0 (TypeScript, Node), een CLI die een lokaal OpenAI-compatibel model (Ollama op max2) test en via `harness worker` jobs claimt. De worker draait in productie als systemd-service op max2 (`agent-harness-worker.service`, `Restart=always`); config in `/etc/agent-harness/worker.json`, secrets in `/etc/agent-harness/worker.env` (root, 0600). De conventie in de repo is dat secrets in de omgeving staan, nooit in config of code — zie manual/readme.

Relevant gedrag van de worker (zie manual/readme en runbooks/idea-chat-worker, runbooks/task-worker):
- De worker claimt IDEA_CHAT-jobs en (met een `task`-blok) TASK_IMPLEMENTATION-jobs; per job schrijft hij een run-dir `runs/job-<jobId>-<epoch-ms>/`.
- Hij sluit jobs zelf af via `update_job_status`: `done` bij succes, anders `failed` met een leesbare fout (o.a. "worker gestopt" bij Ctrl-C/systemd-stop).
- `harness run` sluit af met `completed`, `failed`, `budget_exceeded` of `timed_out` (exit 1 bij het laatste drietal).
- De worker kan ook met exit 1 stoppen bij een mislukte opruim van een achtergebleven harness-container (runbooks/task-worker, "Opruimen"); systemd herstart hem dan.
</context>

<task>
Implementeer in de worker een Slack-melding bij elke mislukte job: zodra een job als mislukt wordt afgesloten, stuurt de worker een bericht naar ons Slack-kanaal via een incoming webhook.
</task>

<constraints>
- Webhook-URL alleen via de omgevingsvariabele `SLACK_WEBHOOK_URL` (in productie toe te voegen aan `/etc/agent-harness/worker.env`); de URL komt nooit in config, code, trace, run-logs of `result.json`.
- Zet `SLACK_WEBHOOK_URL` leeg of afwezig, dan doet de worker exact wat hij nu doet: geen melding, geen ander gedrag, geen fout.
- De melding bevat: job-id, jobsoort (IDEA_CHAT of TASK_IMPLEMENTATION), eindstatus (`failed`, `budget_exceeded` of `timed_out`), de faalreden en de run-dir.
- De melding is best-effort: een mislukte of timeoutende webhook-post (werk een timeout uit) mag de worker nooit breken of de jobuitkomst veranderen; log in dat geval één foutregel.
- Meldingsmoment: één melding per mislukte job, op het moment van de terminale `update_job_status` (dus ook "worker gestopt" bij SIGINT). Stuur geen dubbele melding als de terminale update zelf faalt en er alsnog iets wordt geprobeerd.
- Niet in scope: meldingen bij geslaagde jobs, meldingen op worker-niveau (bijv. de exit-1-omweg van de containeropruim), rate-limiting, een Slack-app of outgoing events.
- Volg de bestaande code- en testconventies van de repo; de webhook-call hoort in de tests gemockt, geen netwerk in de tests.
</constraints>

<done_when>
- `npm run verify` (lint + typecheck + test, zonder netwerk) is groen.
- Er is een unit-test die aantoont: mislukte job → precies één webhook-post met de velden hierboven; webhook-fout of timeout → de job wordt toch correct afgesloten en de worker loopt door; `SLACK_WEBHOOK_URL` afwezig → geen enkele netwerkcall.
- manual/readme (worker-sectie) en de betreffende runbooks (idea-chat-worker, task-worker) zijn aangevuld met de nieuwe omgevingsvariabele en het meldingsgedrag.
</done_when>

<output_format>
De wijzigingen als commits in de repo, plus een korte samenvatting: welke bestanden wijzigen, hoe de melding er in Slack uitziet (voorbeeldbericht) en de exacte stappen om het live te zetten op max2 (waarde toevoegen aan `/etc/agent-harness/worker.env`, herstart).
</output_format>

<check_in>
Ga door zonder te vragen. Vraag eerst wel even als je vastloopt op een ontwerpkeuze die het gedrag van lopende jobs zou kunnen veranderen, of als `SLACK_WEBHOOK_URL` al ergens in de repo of de docs voorkomt met een andere betekenis.
</check_in>
```

Aannames:
- De repo staat op `~/Development/agent-harness` (zowel op je Mac als op max2), zoals in runbooks/idea-chat-worker.
- "Mislukte job" = een job die de worker zelf als `failed`/`budget_exceeded`/`timed_out` afsluit; de worker-crash-omweg (exit 1 door containeropruim) is expliciet uitgesloten als niet-in-scope, omdat die geen job-afsluiting is.
- De melding gaat via één Slack-incoming-webhook per kanaal; er is nog geen Slack-integratie in de repo (geen bestaande code om mee in lijn te blijven).
- De webhook-post gebruikt de ingebouwde `fetch` van Node, zonder nieuwe dependency.
- Het voorbeeldbericht en de live-stappen voor max2 hoort Opus te leveren; de webhook-URL zelf is een geheim en komt dus niet in de code.

Instellingen: effort medium. Geen bijlagen nodig — de documentatie en de repo leveren de context.
