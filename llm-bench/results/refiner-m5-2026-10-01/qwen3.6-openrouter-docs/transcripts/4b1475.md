## Architectuur-overzicht (bron: specs/2026-09-26-agent-harness-v0-design)

De worker (M2 + M3) draait een modelloop met toolcalls. Statusmodel: `queued → running → completed | failed | budget_exceeded | timed_out`. Bij een taakjob komt `VERIFY_FAILED` bij.

Per job-soort worden bij falen `update_job_status` aangeroepen:
- **IDEA_CHAT (M2):** `update_job_status(failed, error: "<status>: <code> <message>")` bij failed/timed_out/budget_exceeded, of `failed` bij leeg antwoord.
- **TASK_IMPLEMENTATION (M3):** `update_job_status(failed, ...)` bij prepare-fout, rode verify (na max retries), budget, timeout, stop, of gewijzigde git-administratie.

De worker-modus CLI is:
```bash
harness worker --config worker.json --out runs [--once]
```

De worker leest config uit `worker.json` (zelfde `${VAR}`-expansie als het v0-manifest), bevat een `model`-blok met `baseUrl`, en verbindt via MCP-stdio naar scrum4me-mcp.

## Worker-config-structuur (M2, specs/2026-09-26-idea-chat-local-llm-design)

```ts
type WorkerConfig = {
  model: { baseUrl: string; name: string; apiKey?: string }
  mcp: { command: string; args: string[]; env?: Record<string, string> }
  allow: string[]
  limits: { maxTurns: number; maxOutputTokens: number; maxWallSeconds: number; maxToolErrors: number }
  waitSeconds: number
}
```

## Tweepersoonsafhandeling (M2, §4.2)

Elke run eindigt in een `finally`-blok:
- `completed`, antwoord niet leeg → `update_job_status(done, ...)`
- `failed` / `timed_out` / `budget_exceeded` → `update_job_status(failed, error: "<status>: <code> <message>")`
- exception → `update_job_status(failed, error: "harness: <message>")`

## Taakjob-afhandeling (M3, §4.3)

Per taakjob: prepare → modelloop → verify → (optioneel herhalen) → git commit → verify_task_against_plan → update_job_status.
Elk faalpad na stap 2: containers killen → `log_test_result FAILED` → `update_job_status failed`.

<task>
Voeg een Slack-melding toe die wordt verstuurd bij elke mislukte worker-job (IDEA_CHAT en TASK_IMPLEMENTATION). De melding wordt verstuurd via een `fetch()`-POST naar een webhook-URL die wordt gelezen uit de omgevingsvariabele `SLACK_WEBHOOK_URL`. De worker mag niet crashen als de melding faalt; een fout bij het versturen wordt gelogd naar stderr maar tast de job-afhandeling niet af.

Vul de volgende gegevens in de melding:
- job_id
- job_type (IDEA_CHAT of TASK_IMPLEMENTATION)
- foutcode (bijv. `MODEL_ERROR`, `VERIFY_FAILED`, `TOO_MANY_TOOL_ERRORS`)
- kort foutbericht (de `error.message` uit de run-uitkomst)
- modelnaam en baseUrl
- run_id

De webhook-POST stuurt een eenvoudige JSON-payload met een `text`-veld dat Slack als blokbericht interpreteert. Gebruik geen extra npm-dependencies; alleen de ingebouwde `fetch()`.
</task>

<constraints>
- Geen nieuwe npm-dependencies. Alleen `fetch()`.
- De Slack-melding mag niet de job-afhandeling blokkeren of crashen veroorzaken.
- Meldingen voor CLI-runs (`harness run`, `harness probe`) worden niet verstuurd — alleen voor jobs die via de worker-modus (`wait_for_job`) zijn geclaimd.
- Als `SLACK_WEBHOOK_URL` niet is ingesteld, sla de melding stil over (geen foutmelding).
- De worker-config (`worker.json`) krijgt een optioneel veld `slack?: { webhookUrl?: string }` als fallback, maar de env-var heeft voorrang.
</constraints>

<done_when>
- De worker verstuurt een Slack-blokbericht bij elke terminale foutstatus (failed, timed_out, budget_exceeded, VERIFY_FAILED) voor zowel IDEA_CHAT als TASK_IMPLEMENTATION jobs.
- Bij afwezigheid van `SLACK_WEBHOOK_URL` en geen `slack.webhookUrl` in de config wordt geen fout gegenereerd en geen melding verstuurd.
- Een falende Slack-aanroep wordt gelogd naar stderr zonder de job-afhandeling te beïnvloeden.
- De melding bevat job_id, job_type, foutcode, foutbericht, modelnaam, baseUrl en run_id.
</done_when>

<output_format>
Het volledige TypeScript-bestand met de wijzigingen, inclusief de nieuwe module voor Slack-notificaties, de aanpassingen in de worker-afhandelingspaden, en de Zod-validatie voor het optionele `slack`-configblok. Korte uitleg van de wijzigingen.
</output_format>

Aannames:
- De `SLACK_WEBHOOK_URL` is een process.env-variabele op max2 (geen hard-coderen).
- De melding moet een Slack blok-JSON zijn (`{"text": "..."}`), geen Rich Text JSON-structuur.
- De worker-log-pipeline (M4) is gescheiden van deze Slack-functie; de melding is een aanvullend alert.
- De TypeScript-code volgt de bestaande structuur: ESM, strict mode, zod-validatie voor config.
- De foutcode komt uit de bestaande `RunResult.status` + `error.code` die al in `result.json` staan.

Instellingen: effort high (dit raakt de worker-afhandelingspaden en vereist zorgvuldige foutisolatie).
