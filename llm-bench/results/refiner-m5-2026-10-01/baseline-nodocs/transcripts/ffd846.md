# Transcript ffd846 (R06: review zonder bestand)

### Gebruiker

Kun je mijn docker-compose op security laten reviewen?

### Model

Twee korte vragen om de review zo nuttig mogelijk te maken:

1. Moet de review focussen op technische configuratiefouten (zoals `privileged: true`, blootliggende poorten, missing healthchecks) of ook op infrastructuur- en IAM-richtlijnen (zoals het gebruik van `latest` tags, root users, hard-coded secrets)? [Standaard: beide, maar met focus op directe technische risico's]
2. Is deze `docker-compose.yml` bedoeld voor productie, ontwikkeling of CI/CD? [Standaard: productie, aangezien dit de strengste security-eisen stelt]

### Gebruiker

Akkoord met je voorstellen. Het is een compose-bestand voor een paar containers op mijn thuisserver.

### Model

Wil je de bestanden alvast plakken, of wil je dat ik de prompt zo schrijf dat jij ze later kunt toevoegen?

[Standaard: ik schrijf de prompt nu, en jij plakt de content in de `<material>` tags bij gebruik]

### Gebruiker

Akkoord met je voorstellen.

### Model

Aan de prompt.

```xml
<context>
Ik heb een `docker-compose.yml` voor een thuisserver met een beperkt aantal containers. Ik wil deze laten reviewen op beveiligingsrisico's.
</context>

<task>
Review de meegeleverde `docker-compose.yml` op beveiligingskwetsbaarheden en beste praktijken.
</task>

<material>
[PLAK HIER JE DOCKER-COMPOSE.YML CONTENT]
</material>

<constraints>
- Focus op directe technische risico's in de configuratie (bijv. privilege escalation, netwerkblootstelling, missing healthchecks, latest tags, root users).
- Vermeld ook infrastructuur- en IAM-richtlijnen (bijv. hard-coded secrets, volume mounts) als deze relevant zijn.
- Gebruik geen algemene "double-check" instructies; baseer je op de specifieke context van een thuisserver.
</constraints>

<done_when>
- Een overzicht van gevonden risico's, gegroepeerd per container of dienst.
- Voor elk risico: de ernst (High/Medium/Low), een korte uitleg, en een concreet advies om het op te lossen.
- Een samenvatting van de top 3 meest kritieke punten.
</done_when>

<output_format>
Een gestructureerd rapport in markdown. Gebruik duidelijke kopjes en lijstjes voor de risico's.
</output_format>
```

Aannames:
- De review is bedoeld voor een thuisserver, dus extreme enterprise-compliance (zoals SOC2) is minder relevant dan praktische risico's.
- De `docker-compose.yml` wordt in de `<material>` tags geplakt bij het gebruik van de prompt.
- Er wordt gevraagd om een balans tussen technische diepgang en bruikbaarheid voor een niet-enterprise context.

Instellingen: effort medium.

Wil je nog iets aanpassen aan de focus van de review?
