# Transcript 94c2bb (R08: agenttaak)

### Gebruiker

Laat Claude Code mijn repo migreren van Jest naar Vitest.

### Model

Enkele vragen om de prompt scherp te krijgen:

1. In welke stack en met welk testopbouw draait de repo? [standaard: Node.js/TypeScript, tests in `src/**/*.test.ts`, geconfigureerd in `package.json` en `jest.config.*`]
2. Moet Claude Code de wijzigingen direct aanbrengen in de repo, of eerst een plan presenteren? [standaard: direct aanbrengen, maar stoppen en vragen vóór het verwijderen van Jest-afhankelijkheden en het wijzigen van CI-configuratie]
3. Wat telt als klaar? [standaard: alle bestaande tests slagen onder Vitest, Jest is volledig verwijderd, en `npm test` werkt zonder wijziging]
4. Zijn er specifieke Jest-functionaliteiten in gebruik die aandacht vragen (mocks, setup files, coverage, snapshot tests, custom matchers)? [standaard: niet bekend, laat Claude Code dit zelf inventariseren en per onderdeel aangeven hoe het overgezet wordt]

### Gebruiker

Akkoord met je voorstellen. Het is een TypeScript-project met ongeveer 200 tests.

### Model

```
<context>
Ik heb een TypeScript-project met ongeveer 200 bestaande tests die nu draaien op Jest. Ik wil de testinfrastructuur migreren naar Vitest, zodat ik de moderne tooling gebruik zonder dat het gedrag van de tests verandert.
</context>

<task>
Migreer de repository volledig van Jest naar Vitest. Inventariseer eerst de bestaande Jest-configuratie, testbestanden, mocks, setup files, snapshots en eventuele custom matchers. Vervang daarna de Jest-afhankelijkheden door Vitest, pas de configuratie aan, en pas de testbestanden aan waar de API-verschillen tussen Jest en Vitest dat vereisen.
</task>

<constraints>
- Wijzig geen productiecode tenzij dat strikt noodzakelijk is om tests onder Vitest te laten draaien; zo’n wijziging moet expliciet worden gemotiveerd.
- Behoud de bestaande testgedraging: dezelfde tests, dezelfde expected results, dezelfde coverage-vanwege-bestanden.
- Gebruik Vitest-native faciliteiten waar mogelijk (bijv. `vi` in plaats van `jest`, Vitest-config in `vitest.config.ts` of `vite.config.ts`).
- Verwijder alle Jest-specifieke dependencies, scripts en configuratie na de migratie.
- Voeg geen nieuwe testbestanden toe en herschrijf bestaande tests niet, tenzij de API-migratie dat vereist.
</constraints>

<done_when>
- Alle ongeveer 200 tests slagen onder Vitest met `npm test` of het equivalent.
- Er zijn geen Jest-afhankelijkheden meer in `package.json` en geen `jest.config.*`-bestanden meer in de repo.
- De coverage-commando’s werken onder Vitest, als die voorheen bestonden.
- Er is een korte migratievermelding bij de commit of in een aparte sectie die aangegeven wat per onderdeel (configuratie, mocks, snapshots, setup) is aangepast.
</done_when>

<output_format>
Werk de bestanden in de repo direct aan. Geef daarna een beknopt rapport met:
1. Een overzicht van de aangepaste bestanden.
2. Een lijst van eventuele API-verschillen die je hebt moeten aanpassen.
3. De exacte commando’s om de tests en coverage te draaien.
</output_format>

<check_in>
Stop en vraag om bevestiging vóór:
- Het verwijderen van Jest-afhankelijkheden uit `package.json`.
- Het wijzigen van CI-configuratie of scripts die tests draaien.
- Het aanpassen van productiecode.
- Het overschrijven of verwijderen van bestaande snapshot-bestanden.
</check_in>
```

Aannames:
- De project gebruikt een standaard Node.js/TypeScript-opstelling met tests in `src/**/*.test.ts` of vergelijkbaar.
- De huidige test- en coverage-commando’s staan in `package.json`.
- De migratie moet de bestaande testgedraging behouden, niet alleen de tests laten draaien.
- Er zijn geen bijzondere Jest-plugins of custom matchers die expliciet genoemd zijn; Claude Code moet deze zelf inventariseren.
- De migratie mag direct in de repo plaatsvinden, maar moet voor bepaalde acties eerst bevestiging vragen.
