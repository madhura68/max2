> Model, beurt 3:
>
> Here is the analysis of the difference between a Product Backlog Item (PBI) and a User Story.
>
> ### 1. The Core Difference: Container vs. Content
>
> The simplest way to understand the difference is to think of it as **Category vs. Specific Type**.
>
> *   **PBI (Product Backlog Item):** This is the **umbrella term**. It refers to *any* item in the Product Backlog. It is a container that can hold a feature, a bug, a technical task, or an experiment.
> *   **User Story:** This is a **specific format** for describing *one type* of PBI: a piece of functionality that delivers value to a user.
>
> **Analogy:**
> *   **PBI** is like the term "Food".
> *   **User Story** is like "Pizza".
> *   Pizza is a type of food, but not all food is pizza (some food is salad, some is soup). Similarly, a User Story is a type of PBI, but not all PBIs are User Stories.
>
> ---
>
> ### 2. Deep Dive: What is a User Story?
>
> A User Story is a tool used in Agile/Scrum to capture a requirement from the perspective of the end-user. It focuses on **value**.
>
> *   **Standard Format:**
>     > *"As a **[role]**, I want **[feature/action]**, so that **[benefit/value]**."*
> *   **Purpose:** To start a conversation about what needs to be built and why. It forces the team to think about the "who" and the "why," not just the "what."
> *   **Characteristics:**
>     *   **Small:** Ideally fits into a single sprint/iteration.
>     *   **Negotiable:** The details are discussed between the Product Owner and the Development Team.
>     *   **Valuable:** It must deliver some form of value to the user or stakeholder.
>
> **Example of a User Story:**
> > *"As a **logged-in user**, I want to **reset my password via email**, so that **I can regain access to my account if I forget it.**"*
>
> ---
>
> ### 3. Deep Dive: What is a PBI?
>
> A PBI is any unit of work that exists in the Product Backlog. While User Stories are the most common PBIs, a PBI can also be:
>
> 1.  **A Bug:** A defect that needs fixing (e.g., *"Login button fails on mobile Safari"*).
> 2.  **A Technical Task:** Work required to support the system but not directly visible to the user (e.g., *"Upgrade database library to version 2.0"*).
> 3.  **A Spike:** A time-boxed research task to learn something new (e.g., *"Research feasibility of AI chatbot integration"*).
> 4.  **An Epic:** A large body of work that is too big to fit in one sprint and must be broken down into smaller PBIs (often User Stories).
>
> **Key Point:** You do not always write a PBI as a User Story. Sometimes you write it as a bug report, a task ticket, or a research note.
>
> ---
>
> ### 4. Comparison Table
>
> | Feature | User Story | PBI (Product Backlog Item) |
> | :--- | :--- | :--- |
> | **Scope** | Specific type of item | Umbrella term for *all* items |
> | **Focus** | User value and experience | Work to be done (any type) |
> | **Format** | *"As a... I want... So that..."* | Flexible (can be a story, bug, task, etc.) |
> | **Audience** | Users, Product Owners, Devs | Product Owners, Devs, Tech Leads |
> | **Example** | *"As a shopper, I want to filter by size."* | *"Fix crash on checkout page"* (Bug PBI) |
>
> ---
>
> ### 5. Why does this distinction matter?
>
> 1.  **Clarity in Planning:** When you look at your backlog, you need to know what kind of work each PBI represents. If a PBI is a "Bug," it might need immediate attention. If it's a "User Story," it needs definition and acceptance criteria.
> 2.  **Prioritization:** Product Owners prioritize PBIs based on value, risk, and cost. A User Story is prioritized for *user value*. A Technical PBI might be prioritized for *system stability*.
> 3.  **Communication:** Using the User Story format ensures you don't forget the "So that..." (the value). If you just write a PBI as a technical task without context, developers might build the wrong thing.
>
> ---
>
> ### 6. Practical Example: Building a Login System
>
> Imagine you are building a login feature. Your Product Backlog might contain these PBIs:
>
> 1.  **PBI 1 (User Story):** *"As a new user, I want to register with my email, so that I can create an account."*
> 2.  **PBI 2 (User Story):** *"As a registered user, I want to reset my password, so that I can regain access if I forget it."*
> 3.  **PBI 3 (Bug):** *"As a user, I see a 404 error when clicking 'Forgot Password' on mobile devices."*
> 4.  **PBI 4 (Technical Task):** *"Set up encryption for password storage in the database."*
>
> **Notice:**
> *   PBIs 1 and 2 are **User Stories** because they describe user value.
> *   PBI 3 is a **Bug PBI** because it fixes a defect.
> *   PBI 4 is a **Technical PBI** because it is work for the developers, not a direct user feature.
>
> ---
>
> ### Summary for Yourself
>
> *   **PBI** = Anything in the backlog.
> *   **User Story** = A specific way to describe a *user-focused* piece of work within that backlog.
>
> You will likely write **User Stories** most of the time because you want to ensure you are building value for users. But you will also have **other PBIs** (bugs, tech debt) that are important but don't fit the User Story format. Both are PBIs; only the user-focused ones are User Stories.

> Model, beurt 2:
>
> Onderstaand de prompt die je direct kunt kopiëren. Ik ga er vanuit dat je een standaard indeling-validatie wilt zonder de complexere specifieke letterregels, en dat JavaScript de meest gangbare context is.
>
> ```prompt
> <task>
> Schrijf een reguliere expressie (regex) die Nederlandse postcodes valideert op basis van de standaardindeling: vier cijfers, gevolgd door een spatie, gevolgd door twee hoofdletters.
> </task>
>
> <constraints>
> - De regex moet alleen de indeling controleren (bijv. '1234 AB'), niet de specifieke geldigheid van de letters volgens de Nederlandse postcodesystemen.
> - De regex moet geschikt zijn om te gebruiken in een string-matching context (bijv. in JavaScript, Python of een andere gangbare taal).
> - Zorg dat de regex exact matcht op de volledige postcode (geen deelstrings die toevallig matchen, tenzij de context dat vereist).
> </constraints>
>
> <output_format>
> - Geef de regex in een codeblok.
> - Leg kort uit wat de onderdelen van de regex betekenen.
> - Geef twee voorbeelden: één geldige postcode en één ongeldige postcode, met een korte uitleg waarom ze wel of niet matchen.
> </output_format>
>
> <done_when>
> De regex herkent geldige Nederlandse postcodes van de vorm [0-9]{4} [A-Z]{2} en weigert formaten die hier niet aan voldoen (bijv. minder dan vier cijfers, ontbrekende spatie, kleine letters).
> </done_when>
> ```
>
> **Aannames:**
> - Ik heb gekozen voor de basis-indeling (`[0-9]{4} [A-Z]{2}`) zonder de specifieke uitzonderingen voor bepaalde beginletters (zoals D, I, O, S, V), omdat je aangaf dat "gewoon" sneller is.
> - De context is algemeen, maar ik geef het uit in een taal-agnoosc vorm met een focus op JavaScript/Python compatibiliteit.
>
