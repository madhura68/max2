# Transcript 25d79f (R06: review zonder bestand)

### Gebruiker

Kun je mijn docker-compose op security laten reviewen?

### Model

Om je een scherpe prompt te geven voor deze security review, heb ik nog vier details nodig:

1. Wat is de belangrijkste focus van deze review (bijv. netwerkisolatie, secret management, of alleen best practices)? [standaard: een brede check op veelvoorkomende Docker beveiligingsrisico's]
2. Moet Opus direct verbeterde code genereren of eerst een rapport met bevindingen en aanbevelingen schrijven? [standaard: eerst een gedetailleerd rapport met risico's en prioriteiten, gevolgd door een voorbeeld van aangepaste code]
3. Heb je specifieke context over de omgeving (bijv. productie vs. development) of eerdere beveiligingseisen die al zijn ingevoerd? [standaard: dit is voor een productieomgeving zonder eerdere specifieke veiligheidsrichtlijnen]
4. Ga je de `docker-compose.yml` inhoud nu inplakken of via een bestand uploaden? [standaard: ik zal de code in de prompt plakken]

### Gebruiker

Akkoord met je voorstellen. Het is een compose-bestand voor een paar containers op mijn thuisserver.

### Model

Hier is de verfijnde prompt voor Claude Opus 5.5, klaar om te gebruiken.

```xml
<context>
Ik beheer een thuisserver met een paar containers die draaien via Docker Compose. Ik wil dat mijn configuratie secure is, maar ik ben niet altijd op de hoogte van de nieuwste best practices. De omgeving is een thuisnetwerk, maar ik wil voorkomen dat kwetsbaarheden openstaan voor het internet of dat gevoelige data lekken.
</context>

<material>
[Paste hier je volledige inhoud van docker-compose.yml]
</material>

<task>
Voer een grondige security review uit op de bovenstaande docker-compose.yml configuratie. Identificeer beveiligingsrisico's, misconfiguraties en afwijkingen van best practices voor Docker-omgevingen.
</task>

<constraints>
- Focus op veelvoorkomende Docker-risico's zoals: gebruik van 'latest' tags, ontbreken van non-root gebruikers, onnodige capabilities (CAP_SYS_ADMIN etc.), blootstelling van ports, gemiste resource limits (CPU/RAM), en secret management.
- Geef voor elk gevonden issue een duidelijke uitleg waarom het een risico is en wat de impact zou kunnen zijn.
- Classificeer elk issue op ernst (Critical, High, Medium, Low).
- Als er geen specifiek risico is gevonden voor een bepaald aspect, vermeld dan expliciet dat de configuratie daar veilig is of dat het niet van toepassing is.
- Vermijd het genereren van code die niet direct nodig is; focus eerst op de analyse.
</constraints>

<done_when>
- Elk bestand, image, port en volume in de compose file is geanalyseerd.
- Alle bevindingen hebben een duidelijke ernst-classificatie en een korte toelichting.
- Er is een samenvatting gegeven van de grootste risico's.
- Er is een voorbeeld van een aangepaste docker-compose.yml gegeven die de kritieke en hoge risico's oplost, met commentaar in de code die uitlegt wat er is veranderd.
</done_when>

<output_format>
1. Een korte samenvatting van de algehele security-status.
2. Een gedetailleerde lijst met bevindingen (per issue: beschrijving, ernst, impact, aanbeveling).
3. Een volledig herschreven docker-compose.yml die de aanbevelingen toepast, inclusief comments die de wijzigingen uitleggen.
</output_format>
```

**Aannames:**
- De server draait Linux en je hebt root-toegang tot Docker.
- Je bent op zoek naar een balans tussen gebruiksgemak voor een thuisgebruiker en goede security-practices (geen overmatige complexiteit die de server onbruikbaar maakt).
- De containers zijn standaard open-source images (zoals Docker Hub) tenzij anders vermeld in de code.

**Instellingen:**
- Effort: medium (geschikt voor analyse en code-refactoring).
- Attachments: Geen, je plakt de code in het `<material>` blok.
