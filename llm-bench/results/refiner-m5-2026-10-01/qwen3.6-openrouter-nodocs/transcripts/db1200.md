### Gebruiker

Ik wil een dashboard voor mijn Ollama-modellen op max2.

### Model

Om een dashboard te bouwen dat werkt met jouw lokale Ollama-installatie, heb ik de volgende details nodig:

1. Welke programmeertaal of technologie wil je gebruiken voor de front-end? (Standaard: React.js met Tailwind CSS, omdat dit snel een strak resultaat geeft)
2. Moet het dashboard alleen de *status* en *configuratie* van de modellen tonen (zoals geheugengebruik, actieve modellen, start/stop), of ook de *gesprekken* (chatgeschiedenis) beheren en tonen? (Standaard: alleen beheer/status; chatgeschiedenis is complexer en vereist een database)
3. Hoe wil je dat de modellen worden gedetecteerd? Ollama draait vaak als lokale service. Moet het dashboard automatisch connecteren met de standaard Ollama API (poort 11434), of moet het configuratie voor een specifieke URL/poort toestaan? (Standaard: connectie met localhost:11434)
4. Is dit een simpele HTML/JS pagina die je lokaal opent, of een volledige applicatie (bijv. met Node.js backend) die je lokaal hostt? (Standaard: een single-page applicatie die direct in de browser draait en communiceert met de Ollama API)

Laat me weten of de standaardopties werken of wat je wilt aanpassen.

### Gebruiker

Akkoord. Extra: alleen tokens per seconde en VRAM, geen login.

### Model

Hier is de definitieve prompt voor Claude Opus 5.5, afgestemd op je wensen (max2 effort, lokaal dashboard, focus op tokens/sec en VRAM, geen auth).

```
<context>
Ik beheer een lokale Ollama-installatie en wil een eenvoudig, lichtgewicht dashboard om de prestaties van mijn modellen te monitoren. Ik heb geen behoefte aan gebruikersbeheer, inloggen of complexe database-opslag. Het doel is snelle visuele controle over hoe "zwaar" een model draait en hoe snel het genereert.
</context>

<task>
Bouw een single-page webapplicatie (HTML, CSS, JavaScript) die direct in de browser werkt en communiceert met de lokale Ollama API (standaard poort 11434).

Het dashboard moet twee hoofdfuncties hebben:
1. Een overzichtstabel van alle geladen (running) modellen.
2. Real-time monitoring van specifieke prestatie-indicatoren voor elk actief model.

Gebruik de Ollama API endpoints `/api/tags` (voor de lijst) en `/api/chat` of `/api/generate` met `stream: true` en `keep_alive: -1` (of de specifieke stats endpoint als beschikbaar in de versie) om data op te halen. Als directe prestatie-API's ontbreken, simuleer of haal de beschikbare metadata op via `/api/tags` en toon deze duidelijk.

Focuspunten per model:
- Tokens per seconde (TPS): Bereken dit op basis van de response tijd van streaming requests.
- VRAM-gebruik: Gebruik de `VRAM_TOTAL` en `VRAM_USED` variabelen uit de Ollama environment of API response (indien beschikbaar), of toon "Niet beschikbaar" als de API dit niet direct exposeert.

Geen login, geen sessieopslag, geen database.
</task>

<constraints>
- Geen authenticatie of login-schermen.
- Geen persistente opslag van gesprekken.
- Focus op lokaal gebruik (localhost).
- Als de API geen directe VRAM-meting toestaat, noteer dit duidelijk in de UI als "VRAM data niet beschikbaar via API", maar toon wel andere beschikbare metadata (zoals modelnaam, versie, en eventuele cache-status).
- Houd de code minimaal en leesbaar. Gebruik geen zware frameworks (geen React/Vue build steps), puur vanilla JS en CSS.
</constraints>

<done_when>
- De HTML-file opent lokaal in een browser.
- Het dashboard toont een lijst van actieve modellen.
- Voor elk actief model worden Tokens/sec (indien berekenbaar via streaming) en VRAM-status getoond.
- De code is compleet, zonder externe dependencies die installatie vereisen (behalve een browser).
</done_when>

<output_format>
- Eén enkel HTML-bestand met ingesloten CSS en JavaScript.
- Uitleg hoe dit bestand te openen en hoe Ollama geconfigureerd moet zijn (bijv. CORS als dat nodig is voor lokaal openen).
- Geen extra bestanden of build-stappen.
</output_format>
```

**Aannames:**
- Je draait Ollama lokaal op `localhost:11434`.
- Je accepteert dat "VRAM" soms alleen via de Ollama CLI (`ollama ps`) nauwkeurig te zien is; de API exposeert dit niet altijd direct per model in alle versies. Het dashboard zal proberen dit via de API te halen, maar valt terug op een melding als het niet lukt.
- "Tokens per seconde" wordt geschat door een dummy-streaming request te doen en de responstijd te meten, aangezien de API dit niet altijd direct als statiek veld teruggeeft.

**Instellingen:**
- **Effort:** `low` (Dit is een eenvoudige frontend taak, geen complexe logica).
- **Attachments:** Geen.

### Gebruiker

### Model

Hier is de bijgewerkte prompt. Ik heb de laadtijd (load time) toegevoegd als derde kernmetric naast TPS en VRAM.

```
<context>
Ik beheer een lokale Ollama-installatie en wil een eenvoudig, lichtgewicht dashboard om de prestaties van mijn modellen te monitoren. Ik heb geen behoefte aan gebruikersbeheer, inloggen of complexe database-opslag. Het doel is snelle visuele controle over hoe "zwaar" een model draait, hoe snel het genereert, en hoe lang het duurt voordat het beschikbaar is.
</context>

<task>
Bouw een single-page webapplicatie (HTML, CSS, JavaScript) die direct in de browser werkt en communiceert met de lokale Ollama API (standaard poort 11434).

Het dashboard moet twee hoofdfuncties hebben:
1. Een overzichtstabel van alle geladen (running) modellen.
2. Real-time monitoring van specifieke prestatie-indicatoren voor elk actief model.

Gebruik de Ollama API endpoints `/api/tags` (voor de lijst) en `/api/chat` of `/api/generate` met `stream: true` en `keep_alive: -1` om data op te halen.

Focuspunten per model:
- **Tokens per seconde (TPS):** Bereken dit op basis van de response tijd van streaming requests.
- **VRAM-gebruik:** Gebruik de `VRAM_TOTAL` en `VRAM_USED` variabelen uit de Ollama environment of API response (indien beschikbaar).
- **Laadtijd (Load Time):** Meet de tijd die het model nodig heeft om te laden (vanaf het moment dat het wordt aangeroepen tot het klaar is voor inference). Dit kan worden geschat door de tijd te meten tussen een `POST /api/tags` (of een status check) en de eerste respons van een generatie-request, of door de `loaded` status uit de API te gebruiken.

Geen login, geen sessieopslag, geen database.
</task>

<constraints>
- Geen authenticatie of login-schermen.
- Geen persistente opslag van gesprekken.
- Focus op lokaal gebruik (localhost).
- Als de API geen directe VRAM-meting toestaat, noteer dit duidelijk in de UI als "VRAM data niet beschikbaar via API".
- Houd de code minimaal en leesbaar. Gebruik geen zware frameworks (geen React/Vue build steps), puur vanilla JS en CSS.
- Toon de laadtijd duidelijk in de tabel, bij voorkeur in seconden (ms).
</constraints>

<done_when>
- De HTML-file opent lokaal in een browser.
- Het dashboard toont een lijst van actieve modellen.
- Voor elk actief model worden Tokens/sec, VRAM-status en Laadtijd getoond.
- De code is compleet, zonder externe dependencies die installatie vereisen (behalve een browser).
</done_when>

<output_format>
- Eén enkel HTML-bestand met ingesloten CSS en JavaScript.
- Uitleg hoe dit bestand te openen en hoe Ollama geconfigureerd moet zijn (bijv. CORS als dat nodig is voor lokaal openen).
- Geen extra bestanden of build-stappen.
</output_format>
```

**Aannames:**
- Je draait Ollama lokaal op `localhost:11434`.
- De "laadtijd" wordt gemeten als de tijd tussen het moment dat het model in de lijst van actieve modellen verschijnt en het moment dat het klaar is voor een request, of via een gesimuleerde meetcyclus.
- VRAM data is afhankelijk van de Ollama-versie; als deze niet beschikbaar is, wordt dit aangegeven.

**Instellingen:**
- **Effort:** `low`
- **Attachments:** Geen
